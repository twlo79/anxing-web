# migrations 146–170 — 第三批封存

25 支，2026-08-27 從 `supabase/migrations/` 搬過來。線上全部跑過了
（`select * from schema_migrations order by name;`），**不要再跑一次**。

## 這一批是什麼

| 範圍 | 主題 |
|---|---|
| 146–147 | 押金移房、押金收款明細（一筆一列 ＋ 觸發器維護 `received_amount`） |
| 148–152 | 運費科目、請款退回草稿清票、支出唯一索引那三支 |
| 153–154 | `profiles` 全員可讀、管家看得到契約與訂單 |
| 155–158 | 憑證下放到逐項、押金加費、加費各自附照片 |
| 159–163 | 事業體帳本（愛皮／洪鯊）：欄位、規則、認列跳過、`orders.account_code` |
| 164–166 | 收款手續費、修部分索引、銀行流水只改摘要 |
| 167–170 | 管家刪訂單的權限與驗證、`expenses.request_id` 與它的驗證 |

## 為什麼是切在 170

**留在原處的是 171 之後** —— 憑證、訂金與暫收管理、付款方式、評價隱藏。
那條線 2026-08 下旬還在演進，寫新的常常要看上一支怎麼寫的。

而 146–170 已經穩定：這兩週改東西沒有回頭翻過它們。

## 這一批裡面值得記住的兩支

**`migration_167` / `168`** —— 「SQL Editor 沒有登入身分」那個教訓的現場。
167 把 `trash_can_delete('orders')` 寫成驗收標準，而 `auth.uid()` 是 null，
所以那一項**每次都是 ❌，跟這支 migration 改了什麼完全無關**。
168 是純驗證、一個字都沒改 —— 要寫「假扮身分」的自檢時照它抄。

**`migration_169` / `170`** —— 「空的但合理」的現場。
`expenses.request_id` 有 FK、有索引、前端也在讀，
**但從來沒有任何一支函式寫過它**，所以支出頁的憑證永遠寫「尚未上傳」。
每一個零件單獨看都正確。

## 程式碼裡還有引用

`src/` 與 `docs/` 底下有不少註解寫著「（`migration_146`）」「（`migration_147`）」之類。
**那些沒有失效** —— 它們是「這個行為是哪一支訂下來的」的指路標，
現在指到這個資料夾。搬走的是檔案，不是那個編號的意義。

## 要重跑的話

不要。線上都跑過了，而這一批裡有好幾支**不是冪等的**
（例如 173 之前的資料回填、索引清理）。
真的要重建環境的話，用 `supabase/schema-baseline.sql`
—— 但先讀主 README 的 9.5，那份**不可信**，要先重生。
