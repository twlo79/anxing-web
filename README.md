### 分組的三個規則（`lib/nav.ts`）

**① 順序就是分組 —— 用「連續相同」切，不是「收集同名」**

`groupNav()` 掃過陣列，遇到不同的 `group` 就開新的一群。
收集同名的話，有人在中間插一項 `group: '收入'`，它會被抓到上面那一群去 ——
而陣列裡它明明在下面。**順序應該完全由陣列決定**，那是唯一一份可讀的真相。

所以**改 NAV 的順序等於改分組**。

**② 先照角色濾，再分群 —— 順序不能反**

反過來的話，整群被濾空時會留下**一個底下什麼都沒有的標題** ——
那比不顯示更糟：它明說有這個東西，只是不給你。
（`cleaner` 只剩「每天」＋分隔線，沒有空標題。）

**③ 沒有標題的那一群收不起來**

`groupOpen()` 讓無標題的群永遠是開的 —— 沒有標題就沒有地方放收合的把手，
收掉之後打不開。

★ 2026-08-28 之後**五群都有名字**，空標題那一群已經沒有成員了。
這條規則留著是給未來的：有人加了一項忘了填 `group`，它會落進那一群，
而那一群不會消失、也不會收起來 —— 至少它還看得見。

### 分隔線：單線分段，雙線分章

群與群之間一條 1px 細線，**最後一群（設定）上面畫兩條**。

★ 上面四群是每天在做的事，「設定」是設完就不再碰的東西 ——
前四群之間是「換一個主題」，設定之前是「換一個層級」。
用同一條線畫兩種分界，等於在說它們一樣重要。

★★ 判斷用**最後一群**（`gi === groups.length - 1`），不是「標籤等於『設定』」——
哪天多加一群、或者「設定」改名，寫死字串會**安靜地失效**；
而「最後一群是收尾」不管群怎麼加都成立。

★ 兩線間距 3px。更近會糊成一條粗線（看起來像畫錯），更遠會讀成兩個獨立的分界。

★ 收合成 52px 時**照樣要畫雙線** —— 那裡沒有標題可讀，
分隔線是唯一的分群線索。

### 收合（2026-08-28）

點群組標題可以收合，狀態存在 `localStorage` 的 `anxing.nav.collapsed`。

★★ **目前所在的那一群一律展開**，不管有沒有被收起來。
從書籤或通知直接進 `/shortterm` 而「收入」是收著的話，
側邊欄會**完全看不出他在哪一頁** —— 沒有任何一項是選取狀態。
而且不去改存起來的狀態，離開那一頁之後它要回到收起來的樣子。

★ 收起來時標題右邊寫**裡面有幾項** —— 只有一個三角形的話，
使用者不知道那底下是 2 項還是 5 項，而「值不值得打開」正是他當下要判斷的事。

★ **側邊欄收合成圖示時（52px）不適用** —— 放不下標題，
沒有標題就沒有三角形，而看不到三角形卻藏著項目的話，那些項目就是消失了。

### 標題長什麼樣（2026-08-28 改版）

**深色粗體 15px ＋ 貼在後面的細線箭頭 ＋ 收起時右側顯示筆數。**

★ 標題不用主色藍 —— 藍色會跟「選取中」那個藍撞。
選取只有一個、標題有五個，**五個藍標題會把唯一的那個答案稀釋掉**。
深色粗體是「層級」而不是「狀態」，那才是標題該有的身分。

★★ 箭頭**貼在標題後面**，不是靠右。靠右的話它離標題有一整個欄寬，
眼睛要跑兩趟才知道「這個字跟那個箭頭是同一件事」。

★★ 箭頭用 **SVG 不用 `▶` / `▼` 字元** —— 那些字元在 Windows 與 macOS 的
寬度和垂直位置都不一樣，標題會左右飄。而那種飄移**只有兩台電腦並排看才發現得了**。

★ 筆數**只在收起時出現**。展開時項目就列在下面，數字是多的；
收起時它回答的正是「值不值得打開」。

> **icon 不能撞衫。** 側邊欄收合成只剩圖示時，🏦 暫收與 💰 帳戶、🤑 營收與 💸 支出
> 都必須一眼分得出來。帳戶那顆換過三次（🏛️ → 🏧 → 📒 → 💰）才定案。

### ⚠ `cleaner` 是收窄選單，不是權限隔離

`migration_131` 建這個角色時就寫明：**`cleaner` 在資料庫眼裡跟 `housekeeper` 相同**。
側邊欄少給幾項，但知道網址就進得去。

要真正隔離得改一批 RLS policy，而漏掉一條的症狀是「他當天打不了卡」——
不會報錯，只會是一片空白。那是一次全面的決定，不該從單張表開始。

### ⚠ RLS 擋下的寫入**回成功且影響 0 列**

這是這個專案最貴的一個坑，今天已經賠掉一整天。PostgREST 遇到 RLS 擋下的
`UPDATE` / `DELETE` 不會報錯，只會回一個空陣列。

**所以每一個寫入都要看改到幾列：**

```ts
const { data, error } = await supabase.from('x').update(patch).eq('id', id).select('id');
if (error) return setErr('儲存失敗：' + error.message);
if (!data || data.length === 0) return setErr('沒有任何一列被更新，通常是權限或狀態已經變了。');
```

只看 `error` 的話，畫面會說「已儲存」而那一列一動也沒動。

### 新開放一個角色看一張表，要動三個地方

漏一個都不會報錯：

| 層 | 檔案 | 漏掉的症狀 |
|---|---|---|
| RLS | `supabase/migrations/*.sql` | 畫面一片空白，沒有錯誤訊息 |
| 側邊欄 | `src/app/(app)/layout.tsx` 的 `NAV` | 進得去但找不到入口 |
| UI 動作 | 頁面內的 `canEdit`、`src/lib/roles.ts` | **按了說成功但沒變** —— 最難查 |

> **前端擋不是安全機制，RLS 才是。** 前端存在的理由只有一個：
> 不要讓人看到一顆按了沒用的按鈕。所以兩邊的角色清單必須一致 ——
> 前端比 RLS 寬會出現「假成功」，比 RLS 窄則是「明明有權限卻看不到按鈕」。
> 清單只留一份，見 `src/lib/roles.ts`。

### 擋阻一定要講話

擋下來卻不說原因，使用者只會看到「按了沒反應」，然後花一整天查。
所有的擋阻都要回答兩件事：**為什麼**、**怎麼辦**。

```
🔒 押金已於 2026-08-20 退還，此單已結清。要修改請洽會計或總管理員。
```

而且訊息要出現在**視窗裡** —— `flash` 的提示條渲染在彈窗後面，
而且幾秒就消失，等於沒說。

# 三、各頁功能與彼此的關係

## 資料的骨幹

```
estates 物業 ──< properties 房源 ──< orders 訂單 ──< revenue_recognitions 認列
                                        │
contracts 契約 ────────────────────────┘（月租單）
```

**`orders` 是全站的交易中心。** 短租、長租月租單、一次性收入（清潔費、取消收入）全都是 `orders` 的一列，用 `source` 區分。營收認列由觸發器從 `orders` 推導，**不要手改**。

## 各頁在做什麼

| 頁面 | 它負責的事 | 資料從哪來 |
|---|---|---|
| **訂單 \| 收入** | 短租訂單與收款。分次收款、加費、移房 | Airbnb 爬蟲 ＋ 人工 |
| **契約 \| 收入** | 長租契約。月租單由契約自動長出來 | 人工建契約，月租單自動 |
| **營收表** | 依認列月份看收入，可下鑽到每一筆 | `revenue_recognitions`（唯讀） |
| **押金管理** | 收退押金，退款要走審核 | 訂單／契約帶入 ＋ 人工 |
| **請款單控管** | 請款 → 兩票核可 → 自動產生支出 | 人工 |
| **支出明細** | 已發生的成本，含遞延母子單 | 請款核可後自動 ＋ 人工 |
| **財務儀表板** | 營收、成本、損益的彙總 | 上面幾張表 |
| **客戶管理** | 房客資料的**彙整**，不是主檔 | 從訂單與契約長出來 |
| **房源評價** | Airbnb 評價、物業與管家評分 | 評價爬蟲 |
| **清潔記錄** | 每次清潔的紀錄與評分 | 清潔爬蟲 |
| **房務管理** | 排班行事曆 ＋ 統計（間數、布巾、清潔點數） | TimeTree 匯入 ＋ 訂單自動長 |
| **出勤** | 打卡、請假、加班、出勤表 | 員工自己打 |

## 三組容易搞混的概念

**① 應繳 vs 認列**（`migration_137` / `138`）

| | 依據 | 產物 |
|---|---|---|
| **應繳** | 契約週期 ＋ 繳法（月繳／季繳／年繳） | `orders` 月租單，**每期整月租金** |
| **認列** | 契約租期 ＋ 日曆月 | `revenue_recognitions`，**首尾按天數比例** |

**兩邊各算各的，互不參照。** 繳法怎麼變，認列一個字都不會動。
7/16 起租的契約：繳款單是 `7/16~8/16` 一整月；認列是 7 月 16 天、8 月整月⋯⋯最後一個月 15 天。首尾相加剛好一個月。

**② 打掃量 vs 布巾 vs 報酬點數**（`lib/hk-payroll.ts`，有測試）

兩人合掃一間：打掃量**各 0.5**、布巾**算 1 間**、報酬點數 = 打掃量 × 房源點數。
同一個數字算兩件事，其中一件一定是錯的 —— 而錯的那件不會報錯。

**③ 固定加費 vs 定期收費**

前者掛在契約下（跟著租期走），後者是獨立的月月產生（垃圾代收費那種）。見〈固定加費 vs 定期收費〉。

# 四、記帳流程（收入 ＋ 支出）

> 這一節是**照著人的動作寫的**，不是照資料表寫的。
> 想知道欄位長什麼樣去看〈各表說明〉；想知道「這筆錢現在該誰動」看這裡。
> 給非工程同仁的版本在 [`docs/會計手冊.md`](docs/會計手冊.md)。

## 4.1 誰在做什麼

```
        收 入                                   支 出
  ────────────────────                    ────────────────────

  🏠 管家   建訂單                          🏠 管家   建請款單、送審
              ↓                                        ↓
  🧮 會計   確認收款                        👔 主管   核可（一票）
              ↓                                        ↓
  ⚙️ 系統   自動認列營收                     🎩 總經理  核可（一票）
                                                       ↓
                                           🧮 會計   排匯款、確認出款
                                                       ↓
                                           ⚙️ 系統   自動產生支出
```

**★★ 兩條流程的形狀是反過來的，這是刻意的。**

收入是「先有事實、後補確認」—— 房客已經住了，錢晚一點才到。
支出是「先確認、後有事實」—— **錢還沒出去，先問過再說**。

所以收款可以先記了再說，而請款單沒核可之前**不會產生任何一筆支出**。

> ⚠ **選單與 RLS 是兩層。** 上面畫的是「正常情況下誰做」，
> 不是「資料庫擋不擋得住」。`migration_154` 之後**管家也改得動訂單收款** ——
> 側邊欄沒藏、RLS 也放行。詳見 2.2 與 2.3。

---

## 4.2 收入：建單 → 收款 → 認列

```
① 建訂單 ────► ② 開單時決定三件事 ────► ③ 收款（可多次）────► ④ 收滿
   🏠 管家         發票 / 加費 / 費用類別       🧮 會計              ⚙️ 自動結清
                                                  │
                                                  └─► 銀行扣了手續費？→ ⚙️ 自動產生一筆郵電費支出
```

### ① 建訂單 —— 訂單頁（`/shortterm`）

| 來源 | 誰建的 |
|---|---|
| Airbnb、Agoda | **爬蟲每天自動進來**，不用人建 |
| 私下、一次性收入 | 右上角「＋ 新增訂單」 |
| 長租月租單 | 由**契約**推導，在契約頁的「收租」視窗看 |

★ `orders` 是全站的交易中心 —— 短租、月租、一次性收入全都是它的一列，用 `source` 區分。

### ② 開單時要決定的三件事

**（a）要不要開發票**

勾了「需開立發票」→ **收款視窗才會出現發票號碼欄位**。
沒勾就永遠不會問你要號碼。抬頭留空的話用客戶名稱。

> 發票是**人自己去平台開**的，系統只負責提醒與記號碼。
> 契約那邊還會多一張「待開發票」清單（回溯本月往前幾個月）。

**（b）固定加費 vs 一次性費用 —— 這兩個常常搞混**

| | **固定加費** | **一次性費用（加費）** |
|---|---|---|
| 掛在哪 | **契約**底下 | **訂單**底下 |
| 多久一次 | 跟著租期，**每一期都產生** | 只有這一次 |
| 例子 | 每月車位費、管理費 | 清潔費、修繕費、賠償 |
| 資料 | `contract_recurring_charges` → `CFEE_` 子單 | `source='oneoff'` 的子單 |
| 在哪加 | 契約頁 → 編輯 → 固定加費 | 訂單頁 → 編輯 → ＋ 新增加費 |

★ 一次性費用可以選「**從押金扣除**」（要有未退的押金才給選）。
選了之後那筆錢不用另外收 —— 退押金的時候直接扣掉。

**（c）費用類別（會計科目）**

只有一次性收入用得到。房租類的一律 null —— **不要留著切換來源前選的值**。

### ③ 收款 —— 訂單頁的「收款」按鈕

**一張單可以收很多次**（`order_payments`）。每一筆各自填日期、金額、方式、帳號。

★★ **銀行扣手續費的那一格：金額填「房客付的」，不是「你看到的」。**

房客匯 10,000、銀行扣 30、帳上進 9,970 —— 金額欄要填 **10,000**，
再勾「銀行扣了手續費」填 30。畫面會**即時算出「實際進帳 9,970」**給你跟對帳單核對。

| 填法 | 營收 | 郵電費支出 | 對不對 |
|---|---|---|---|
| 填 10,000 ＋ 手續費 30 | 10,000 | 30 | ✅ |
| 直接填 9,970 | 9,970 | 0 | ❌ 少認 30 的營收，而且**永遠不會有人發現** |

那 30 元會**自動變成一筆郵電費支出**（`migration_164`），
而且是冪等的 —— 改金額、改成現金、刪掉整筆收款，那筆支出都會跟著更新或消失。

> 這跟請款單的「不內扣」是**同一件事、反方向**：
> 請款是我方付款被扣，收款是我方收款被扣。兩邊都要記成我方成本。

### ④ 收滿 → 自動結清

收滿了自動標記整期已收。**超收不自動** —— 而且會告訴你為什麼：

> 「金額可能填錯了，所以沒有自動結清。確認無誤請自己按『確認收款』。」

★ 沒收滿時不解釋 —— 畫面上「尚欠 $3,000」就是答案，再多一句話是雜訊。

### ⑤ 認列 —— 這一步沒有人要做

觸發器依入退房日期把金額拆成月份 → `revenue_recognitions`。
長租走另一支，**依契約推導，不看訂單怎麼開**（`migration_137`/`138`）。

★★ **`revenue_recognitions` 不要手改。** 它是推導出來的，
手改的值下一次觸發器跑就沒了，而且不會有任何訊息。

### ⚠ 平台代收不用記收款

Airbnb、Agoda、Airbnb 取消收入 —— 錢是平台收的，不經過我們的帳戶。
硬要記只會多出一堆假欠款。

## 4.3 支出：請款單 → 核可 → 匯款 → 支出

```
① 建單 ──► ② 憑證 ──► ③ 送審 ──► ④ 核可 ──► ⑤ 排匯款 ──► ⑥ 確認出款 ──► ⑦ 支出
  🏠 管家    共用/逐項   🏠 管家    👔🎩 兩票   🧮 會計       🧮 會計         ⚙️ 自動
                                    未滿 3,000                 ★ 填了就鎖住
                                    直接放行
```

### ① 建請款單 —— 請款單控管（`/purchases`）

**一張單可以有很多項目。** 每一項各自填：名稱、金額、**用途**、（選填）房源。

用途只有三種：

| 用途 | 意思 | 進哪一本帳 |
|---|---|---|
| 物業 | 某一棟的花費 | 安幸・物業成本 |
| 安幸辦公室 | 公司的花費 | 安幸・營業費用（**不分攤到物業**） |
| 其他事業體 | 愛皮 / 洪鯊 | 愛皮帳 / 洪鯊帳 |

★★ **辦公室費用不分攤到物業** —— 攤下去的話某一棟會出現它從來沒花過的錢。

★★ **一張單只能有一本帳。** 一項選安幸、一項選愛皮是不行的，
`pri_book_guard` 會在**資料庫**擋下來（`migration_160`）。
不是只有前端藏選項 —— 前端擋不住重新整理後的舊畫面。

> 愛皮／洪鯊的支出**另外開一張單**。

### ② 憑證：共用一張，還是逐項各一張

| | **共用憑證** | **逐項憑證** |
|---|---|---|
| 什麼時候 | 一張發票涵蓋整張單 | 每一項各有各的收據 |
| 填在哪 | 單頭一個號碼、一張圖 | 每一項各自的號碼與圖 |
| 畫面顯示 | 那個號碼 | 「3 / 5 項填好」 |

新單**預設逐項**（`migration_155`）。有項目沒有憑證可以勾「無憑證」。

### ③ 送出審核

★★★ **未滿 NT$3,000 的單，送出當下直接變成已核可** —— 沒有人需要按。

門檻寫在資料庫的 `pr_apply_status()` 觸發器裡，不是前端。
前端算的話，改前端就能繞過審核。

### ④ 核可：幾票

| 這張單是誰的帳 | 要幾票 | 誰 |
|---|---|---|
| **安幸** | **兩票** | 主管一票 ＋ 總經理一票 |
| **愛皮 / 洪鯊** | **一票** | 只要總經理（`migration_160`） |

★ **會計不能核可。** 他能建單、能排匯款、能確認出款 —— 就是不能投票。

★★ **駁回、或退回草稿，兩張票都會被清掉。**

內容改了就等於重來一次。不清的話，「核可後改收款帳號」就能把錢導到別的地方，
**兩票白審**。清票是資料庫做的，不是前端。

### ⑤ 排匯款（可以跳過）

填**預定匯款日**與**安幸付款帳號**。這一步只寫計畫，**不碰出款日** ——
錢還沒出去，不該產生支出。

### ⑥ 確認出款 —— 錢真的出去了

填**實際出款日**。匯款或信用卡**一定要選出款帳戶**：
「沒有它就不知道錢從哪個帳戶出去。」

★ 這道必填綁在「確認出款」而不是「排匯款」—— **排匯款可以跳過，
把必填綁在可跳過的步驟上等於沒綁。**

★★ **出款日填了就鎖住，不能改。** 要調整只能撤銷整張單，或直接到支出頁改。

### ⑦ 支出自動產生

出款日一填，觸發器 `gen_expenses_from_pr()` 產生 `expenses`。

- **匯款手續費「不內扣」** → 多一筆郵電費支出（`migration_83`）。改成內扣或金額歸零，那筆會自己消失
- **遞延**：一次付一年的保險費拆成母單 ＋ 12 張子單。
  母單的 `amount` 是「這一期認列多少」，`gross_amount` 才是實付總額

★ 已產生支出的單**不能撤銷** —— 支出是錢真的花掉的紀錄，
連動刪除會讓兩邊對不上，而且復原也不會重新產生。

## 4.4 三個一定要記得的

**① 名目 ≠ 科目**（`migration_90`/`91`）

名目是**給人看的**（「三樓冷氣維修」），科目是**給帳看的**（「修繕費」）。
兩個都要填，而且不會互相推導。

**② 損益是認列基礎，不是收付基礎**

問的是「這段期間**發生了什麼**」，不是「錢進出多少」。
所以八月住的房客九月才付錢，那筆營收算八月的。

**③ 觸發器維護的東西不要手改**

`revenue_recognitions`、`orders.paid_amount`、由請款單產生的 `expenses` ——
手改的值下一次同步就沒了，**而且不會報錯**。

詳見〈錢的流向〉與 [`docs/會計手冊.md`](docs/會計手冊.md)。

## 4.5 採購需求 → 請款單（`migration_218` / `219`，2026-09-05）

採購需求是「想到才提」的清單（房務管理的第三個分頁）；請款單是「請公司付這筆錢」。
兩張單本來各走各的 —— `migration_140` 把資料庫那一半做完了，
但**前端沒有任何一行程式會把需求項目的狀態往前推**，所以需求單永遠停在「尚未採購」。

### 誰做什麼

| 角色 | 看得到 | 做得到 |
|---|---|---|
| 房務 / 管家 | 自己提的需求 | 提需求、看狀態（唯讀） |
| 會計 / 經理 / 總經理 | 全部 | 勾選、建請款單、標為已採購、手動改狀態 |

★ 勾選框與動作列**只有會計以上看得到**。
看得到卻按不動的按鈕比沒有那顆按鈕更糟 —— `purchase_demand_items`
的 `pdi_write` policy 也是這樣寫的。

### 兩條路

```
A 走請款流程   勾項目 → 建請款單 → 填金額 → 送出審核 → 已採購
B 零用金直接買 勾項目 → 標為已採購                （不產生請款單）
```

B 的確認視窗會明講「這條路**不會**產生請款單」——
兩邊都顯示「已採購」的話，看不出是哪一條路走完的。

### 建請款單時自動填入什麼

| 請款項目欄位 | 從需求項目哪裡來 |
|---|---|
| 品名 | `item_name` |
| **金額** | **`null`（待填）—— 不是 0**，見下 |
| 用途 | `purpose_type`（`office` 時 `estate_id` 一律清成 null） |
| 物業 | `estate_id` |
| 備註 | `spec`（規格） |

★ **規格進備註不併進品名**。併起來「衛生紙*1箱 大包裝」會被當成一個品項名稱，
而品名是要印在單子上給人核的。

★★★ **金額帶 `null` 不是 0**（`migration_218` 把 `not null` 拿掉了）。
帶進去的當下還不知道金額 —— 要先詢價。而 0 在請款單上是**合法的值**
（贈品、換貨、對方吸收），畫面上「0」跟「還沒填」長得一模一樣。
拿 0 當待填的話：送審擋不住、主管與總經理各按一次核可**兩個人都不會發現**、
付款出去少一筆錢，而那筆需求還在等。

所以請款單頁的規矩是：**空白顯示「待填」、存草稿不擋、送審時逐項擋並唸出品名**。
`sync_pr_total()` 用 `sum(amount)`，SQL 的 `sum` 忽略 null，
所以單頭總額會自動只加已填的那幾筆 —— 列表與抽屜都會加註「N 項待填」。

### 狀態怎麼走（三支觸發器維護）

| 項目狀態 | 顯示 | 誰把它推到這裡 |
|---|---|---|
| `pending` | 未採購 | 建單時的預設 |
| `quoted` | 已詢價 | 會計手動 |
| `requested` | 已進請款 | 前端「建請款單」時寫入 |
| `done` | **已採購** | `trg_pr_take_demands`：請款單 `draft → pending`（送出審核） |
| `cancelled` | 已取消 | 會計手動 |

| 事件 | 觸發器 | 做什麼 |
|---|---|---|
| 請款單送出審核 | `trg_pr_take_demands` | `requested → done` |
| 請款單抽回草稿 | `trg_pr_take_demands` | `done → requested` |
| 請款單被駁回 | `trg_pr_reject_demands`（`migration_140`） | 退回 `pending`、清 `request_item_id` |
| **刪掉請款項目** | `trg_pri_release_demands` | 退回 `pending`、清 `request_item_id` |

★ **抽回草稿那一半是必要的**。不處理的話，會計把送出的單抽回來改，
需求單還顯示「已採購」—— 一個假的完成狀態比沒有狀態更糟，它讓人以為事情辦完了。

★★★ **刪除那一支補的是一個會卡死資料的洞**。外鍵是 `on delete set null`，
所以刪掉請款項目時 `request_item_id` 被清成 null，**可是 `status` 沒有人改**。
那一項會顯示「已進請款」卻點不到單號，而且因為 `isTakeable('requested')` 是 false，
**再也不能被帶進任何請款單** —— 前端沒有任何按鈕救得回來。
它必須是 `BEFORE DELETE`：`AFTER` 的話外鍵的 set null 可能先跑掉，
那時 update 找不到任何一列，而它**回成功、影響 0 列、沒有錯誤**。

★ 兩支都是 `SECURITY DEFINER`。觸發器裡的 UPDATE 一樣吃 RLS，
而 `pdi_write` 只放行會計以上 —— 刪自己那張請款單的可能是管家。

### 單頭狀態與「已採購」

`demand_rollup()` 維護 `purchase_demands.status`（四個值：`open`/`partial`/`done`/`cancelled`），
而**畫面顯示的是前端 `demandProgress()` 當場從項目算出來的**。

★★ 「已採購」是**顯示字，不是第五個 status 值**。加第五個值要改資料庫 check、
改 `demand_rollup`、改前端三處 —— 而這件事只是要讓人看得懂那一行字。
規則：全部進請款的項目都送審完（`paid === taken > 0`）才顯示「已採購」並轉綠。

★ **已知不一致**：`demand_rollup` 把 `cancelled` 跟 `requested`、`done` 算成同一組，
所以整張單全部取消時資料庫存 `done`；而前端把取消的剔除，算出來是「尚未採購」。
目前畫面顯示前端那個所以看起來正常，但**哪天有報表直接讀那一欄就會對不上**。

### 手動改狀態（逃生口）

會計以上可以在每一項的下拉直接改。已經接到請款單的只給三個選項
（已進請款／已採購／退回未採購）—— 不給改成「已詢價」，
那會變成「還在詢價中，但錢已經在請款單上了」，兩邊各說各話。

★★ **退回未採購一定要清掉 `request_item_id`**（`manualStatusPatch()` 負責）。
不清的話會留下「未採購但接著請款單」的項目，它可以被再帶一次 ——
同一筆錢出現在兩張請款單上，而總額只是「比較大」。

規則寫在 [`src/lib/demand-to-request.ts`](src/lib/demand-to-request.ts)（33 tests）
與 [`src/lib/purchase-demand.ts`](src/lib/purchase-demand.ts)。

## 4.6 稅務管理：進項從支出帶入（`migration_220`，2026-09-05）

營業稅是雙月期（起月一定是奇數）。銷項從平台下載的 excel 上傳；
進項本來只能手 key —— 而那些發票的資料**支出頁上早就有了**。

### 帶入的規則

進項分頁的「⬆ 從支出帶入」列出**同一期、有填憑證號碼、還沒帶過**的支出。

| 進項發票欄位 | 從支出哪裡來 | 接不到時 |
|---|---|---|
| 發票日期 | `spent_on` | — |
| 發票號碼 | `voucher_no` | **沒填的整筆不出現** |
| 廠商 / 統編 | `purchase_requests.payee_company` / `payee_tax_id`（經 `expenses.request_id`） | 留空，人自己補 |
| 品名 / 摘要 | `item_name` / `note` | — |
| 物業 / 房源 | `estate_id` / `property_id` | — |
| 總金額 | `amount`（**含稅**的實付金額） | — |
| 銷售額 | `round(amount ÷ 1.05)` | — |
| 稅額 | `amount − 銷售額` | 逐筆可改 |
| 稅碼 | 合統一發票格式 → `25`；不合 → `X` | 稅碼是必填，不能留空 |
| 收支帳 | 支出的 id | — |

★★ **稅額用相減算，不是 `round(銷售額 × 0.05)`**。
兩個各自四捨五入的話 `net + tax` 可能不等於 `total`，
而 `tax_invoice_amount_chk` 會擋下來 —— 錯誤訊息是一句 SQL 例外，填表的人看不懂。

★ **`expenses` 沒有稅額欄、沒有未稅欄、也沒有賣方統編欄**（2026-09-05 查證，
三十個欄位裡一個都沒有）。所以統編只能走請款單那條路 ——
實測上一期 89 筆有憑證的支出裡，81 筆接得到請款單，**其中只有 25 筆填了統編**。

### ★★★ 這是預填，不是答案

反推對**免稅**是錯的 —— 房租、保險、薪資、國外服務沒有 5% 進項稅，
而反推照樣給它一個。那個數字看起來很正常，然後進到 401 的進項稅額裡。

三層緩衝：

1. 憑證號碼不合統一發票格式（**兩個英文字母 ＋ 八個數字**）的
   → 稅碼 `X`、稅額 **0**、**不預設勾**。實測上一期 89 筆裡有 30 筆是這種
   （`免用統一收據`、`0346`、`S80516012`、`BB0G597056`⋯）
2. 帶入前**每一列的稅額都可以改**（改稅額時銷售額跟著動，讓 `net + tax = total` 永遠成立）
3. `source` 存成 `'expense'` —— 之後查「這個數字哪來的」看得出是反推的

★ 稅碼標籤是刻意露在畫面上的。只把勾勾拿掉的話，使用者會以為是系統漏了那幾筆。

### 防重複

★★★ 帶兩次的話進項稅額憑空多一份，而 401 上只會顯示成「應繳比較少」——
**沒有任何地方會叫**。

- 前端：`importable()` 濾掉已經有 `expense_id` 紀錄的（查**整家公司**，不是只有這一期 ——
  同一筆支出被帶到別期去過的話，這裡也不該再出現）
- 資料庫：`tax_invoice_expense_uniq` 部分唯一索引（只管 `expense_id is not null`，
  手 key 與上傳的都是 null，那些不該互相排擠）

★★ **外鍵是 `ON DELETE SET NULL`，不是 CASCADE**。
CASCADE 的話刪掉一筆支出會連帶刪掉一張**已申報**的發票 ——
那張發票在財政部那邊有紀錄，這邊刪掉之後已結算期別的數字就再也對不回去了。
而刪支出是很日常的動作，那個人不會知道自己順手改了報稅的數字。

### 結算

`銷項稅 − 進項稅 − 上期累積留抵` → 大於 0 是應繳、小於等於 0 是累積留抵（兩者互斥）。
**結算＝凍結**：已結算的期別讀的是當初申報的四個數字，之後補登發票不會動到它們。
作廢的發票不算進申報數，但列要留著（發票號碼是連號的）。

規則寫在 [`src/lib/tax.ts`](src/lib/tax.ts)（53 tests）
與 [`src/lib/tax-from-expense.ts`](src/lib/tax-from-expense.ts)（29 tests）。

# 五、三條錢的流程（請款 / 押金退款 / 押金加費）

> 這一節是 2026-08 重寫的。三條流程刻意做成**同一個形狀** ——
> 核可的人在「請款審核」看到的是同一份清單，他不在意那筆錢是採購還是退押金。
> 兩邊按鈕不一樣的話，每次都要先想「這筆是哪一種」。

## 5.1 一眼看懂三條流程

```
請款單                    押金退款                  押金加費
─────────────────         ─────────────────         ─────────────────
填單 draft                （由訂單/契約同步產生）    在押金頁或訂單頁新增
  ↓ 送審                    ↓ 送出退款審核             ↓ 立刻生效
pending                   pending                   （不需審核）
  ↓ 主管✓ ＋ 總經理✓        ↓ 主管✓ ＋ 總經理✓
approved                  approved                  加費直接影響「應退」
  ↓ 排匯款                  ↓ 排匯款                  ↓
  ↓ 確認付款日              ↓ 確認退款日              退款完成後鎖住
產生支出                   已退款 ＋ 加費轉營收
```

**兩條審核流的動作完全對齊**（2026-08-22）：

| 動作 | 請款單 | 押金退款 | 誰能按 |
|---|---|---|---|
| 送審 | 送出審核 | 送出退款審核 | 會計／主管／總經理 |
| 核可 | 兩票 | 兩票 | 主管一票、總經理一票 |
| 駁回 | ✓（清票，留原因） | ✓（清票，留原因） | 主管／總經理 |
| 排款 | 排匯款 | 排匯款 | 會計／主管／總經理 |
| 確認 | 確認付款日 → 產生支出 | 確認退款日 → 已退款 | 會計／主管／總經理 |
| 撤銷 | 整張移到回收桶 | 退回未送審（押金本身留著） | 會計／主管／總經理 |

> **為什麼撤銷的行為不一樣**：請款單是人建的，撤掉就沒了。
> 押金是訂單/契約**同步過來的** —— 刪掉隔天觸發器又會長回來，
> 所以「撤銷」只能是把退款申請退回未送審。

## 5.2 請款流程

```
draft ──送審──► pending ──主管✓＋總經理✓──► approved ──排匯款──► 確認付款日 ──► 產生支出
  ▲                 │                                                          ↑
  └──── 駁回 ────────┘                                          錢真的出去才記帳
```

**免核門檻**：總額 < NT$ 3,000 送出即核可（兩票全免）。
**開放自核**：主管送的單那一票由他自己投（`migration_32`）。

### 憑證：逐項或共用（`migration_155` / `156`）

原本憑證號碼是**整張單一格**。十七張不同收據沒地方各自放，填單的人就用頓號串成一串，
而 `gen_expenses_from_pr` 把整串複製給**每一筆**支出 ——
結果計程車那筆的憑證號碼裡混著住宿的發票號。

現在：

| 模式 | 誰填 | 什麼時候用 |
|---|---|---|
| **逐項**（預設） | 每個請款項目各填自己的 | 一般情況 |
| **共同憑證**（勾選） | 整張單共用一個號碼 | 真的只有一張發票、拆成多個項目報帳 |

- 勾了共同憑證，項目上的號碼**留著但不使用**（灰掉）—— 取消勾選就回來
- 每個項目各自有「無憑證」勾勾。**「無憑證」與留空白是兩件事**：前者是查過確定沒單據，後者是還沒填
- 送審時會提醒哪幾項沒填，但**不擋**（憑證選填）
- 既有的 59 張單全部回填成共同憑證 —— 舊單畫面完全沒變

> **既有 36 筆支出的憑證號碼仍然是那串頓號字串。** 不回頭改 ——
> 系統分不出那一串裡哪個號碼對應哪個項目（那個資訊從來沒存過）。
> 所以支出頁的截斷顯示（`src/lib/voucher.ts`）不能拿掉。

### 出款日填了就鎖住

`gen_expenses_from_pr` 裡刻意**沒有 elsif** —— 出款日只在「從無到有」時產生支出，
之後改不了。有遞延認列時，母單日期被改而子單留在原地，母子單就散了。

## 5.3 押金退款流程（`migration_61`，2026-08-22 改成三段式）

```
暫收中
  │  送出退款審核：房客收款帳戶 ＋ 退款方式
  ▼
待核可 ──主管✓ ＋ 總經理✓──► 已核可
  │                            │  排匯款：預計匯款日 ＋ 安幸付款帳號
  │                            ▼
  │                          待匯款
  │                            │  確認退款日：實際退款日 ＋ 安幸付款帳號
  └──駁回（清掉兩票）           ▼
                             已退款
```

### 為什麼分成「送審」與「排匯款」兩步

以前預計匯款日與安幸付款帳號在**送審時就必填**。但送審當下常常還不知道
會從哪個戶頭出、哪天出 —— 於是大家隨便填一個再回來改，
**而改動會清掉核可票、退回重審**。

移到核可後的「排匯款」就沒有這個問題。審核者要看的是「錢退給誰」，
不是「我方哪天從哪個戶頭出」。

**帳號在確認退款時會再問一次** —— 實務上真正匯出去的戶頭常常跟排定的不同，
而排定的那個一旦錯了就再也沒機會改（請款單踩過同一個坑）。

### 兩個帳戶方向相反

| 欄位 | 是誰的帳戶 | 錢的方向 |
|---|---|---|
| `payee_bank_code` / `payee_name` / `payee_account` | **房客的** | 錢退到哪 |
| `returned_account` | **我方的**（對應 `payment_accounts.code`） | 錢從哪出 |

### 紅線是 `returned_on`，不是 `refund_status`

錢匯出去之後 `refund_status` 仍然是 `approved` —— 那一欄記的是「審過了」，
不是「還在等」。只看它就會對一筆早就退完的押金說「等待匯款」。

### 撤銷退款申請（2026-08-22）

退回未送審，**兩票一起清掉**。不清的話下次重新送審會帶著舊的兩票進來：
看起來已經核可，而根本沒有人重新看過。

房客帳戶與退款方式**留著不清** —— 那是查得到的事實，清掉只是讓人重打一次。
清單見 `src/lib/deposit-refund.ts` 的 `cancelPatch()`。

## 5.4 押金加費：從押金扣款（`migration_157` / `158`）

房客退房時扣了 1,100 元管理費：

```
押金        310,000
管理費       −1,100
────────────────────
應退        308,900   ← 送退款審核的金額
```

退款完成後：押金記「已退 310,000」（全額結清），其中 308,900 退現金、1,100 轉營收。
**兩個數字都對**，只是回答不同問題：押金結清了沒、實際匯出多少。

### 一筆資料，兩邊都是視圖

加費**就是 `orders` 的一次性子單**（`source='oneoff'`），多一個 `deposit_id`：

| 看的地方 | 看到什麼 |
|---|---|
| 押金頁 | `orders where deposit_id = 這筆押金` → 扣款明細與應退小計 |
| 訂單頁 | 本來就看得到那張子單，多顯示「從押金扣除」 |
| 營收報表 | **完全不用改** —— oneoff 本來就進營收 |

> 另開一張 `deposit_deductions` 表的話，兩邊各記一次，總有一天對不起來 ——
> 而那天你只會看到「押金明細加起來跟營收不一樣」，兩邊都說自己是對的。

### 兩個入口

- **押金頁** → 管理押金 → 加費區塊 → 新增
- **訂單頁** → 加費那列 → 收款方式選「從押金扣除」

訂單頁那個選項**只在查得到同一張訂單的未退押金時才出現**。
查法走 `deposits.order_id` / `contract_id`，**不比房號** ——
房號比對的話同房號跨房客、跨期都會中，而扣錯人的押金畫面上看不出來：
金額對、房號對，只有「是誰的錢」錯了。查到 0 筆或 2 筆以上都不給選。

### 幾條規則

| 規則 | 擋在哪 |
|---|---|
| 加費合計不能超過押金（應退不能是負數） | `trg_order_fee_deposit_guard` ＋ 前端 |
| 已退的押金不能再掛加費 | 同上 |
| 押金退掉之後**整張訂單鎖住** | `trg_orders_lock_guard` ＋ 前端提示 |
| 會計與 super_admin 可以解鎖修改 | 同上（完全鎖死的話打錯字只能下 SQL） |
| 匯入排程不受鎖定影響 | `current_role_of()` 是 null 就放行 |

> **`current_role_of()` 是 null 就放行是刻意的洞**：匯入用 service key 連線沒有 `auth.uid()`。
> 擋下來的話 Airbnb 每晚同步會整批中斷，而症狀是「昨天的訂單沒進來」——
> 沒有人會聯想到是押金退款造成的。**這道是防手滑，不是防惡意**，真正的權限在 RLS。

### 費用日期決定營收落在哪個月

預設帶 `實際退款日 → 預計匯款日 → 今天` 第一個有值的，**但一定可以改**。
帶錯不會報錯，只會讓那筆錢落在別的月份。

### 每筆加費各自可以附照片（`migration_158`）

掛在**那一筆**（`attachments.order_id`，路徑前綴 `of/`），不是掛在押金底下。
一筆押金可以扣好幾筆加費 —— 都掛在押金上的話分不出哪張對哪筆，
而房客問「憑什麼扣 800」時那是唯一能拿出來的東西。

### 核可之後加費被改動

使用者選了「確認退款前都能改」。副作用是主管核的是 308,900，
核完之後有人把加費改成 2,000，實退變 308,000 ——
**核可紀錄上的金額不再是實際退的金額**。

系統**不擋**，但會在押金列與確認視窗顯示：

> ⚠ 核可金額 308,900 ≠ 目前應退 308,000

系統負責看見，人負責決定。

```
      ├─ Airbnb 訂單 ──→ /api/import/airbnb-orders ──→ airbnb_snapshots（快照）

```

**全部帶 `x-import-key`**（環境變數，不寫進任何檔案）。

## 為什麼中間隔一張快照表

爬取與對帳分兩階段。爬蟲只負責「把看到的存下來」，**不動 `orders`**；對帳是另一步，而且**只自動做兩件事**：新訂單、取消。其餘一律進「同步建議」讓人決定。

理由寫在〈判斷原則〉：**建議，不自動。系統負責看見，人負責決定。**

## 幾個關鍵規則

- **比對的鑰匙是 Airbnb 確認碼**，不是房客名或日期
- **人工編輯過的訂單，爬蟲一律不動**
- **「不見了」要配掃描範圍** —— 沒掃到不等於不見了，連續兩輪才標記（`migration_125`）
- **一間房可以有多個 `listing_id`**（下架後重新上架），走 `property_listings` 對照（`migration_127`）
- **匯入完成會發推播**，內容是聚合的一則，不是每筆一則

某天機關改了標題或撤掉公告，使用者的筆記就會掛在一個不認得的東西上。

### ★★ 爬蟲給不出來的兩個欄位

爬蟲每筆只有 `title` / `date` / `url` / `agency`。

| | |
|---|---|
| **截標日期** | ❌ `date` 是**公告日期**，兩者常差好幾週。截標日期在各網站詳情頁裡，九個格式都不同 |
| **地址** | ❌ 完全沒有。標題裡有時提到，但常是「44 宗」這種 |

**兩個都留空，不猜。** 填錯截標日期的後果是錯過投標，而那正是沒有人會發現的那一種 ——
清單上看起來已經填好了。所以：

- `tenders.due_on` 可以是 null，畫面上寫「未填」而不是留白
- 「截標日期未填」是一張**統計卡**，不是小標記 —— 它永遠會有存量
- 加星建檔後，編輯視窗最上面就寫「還沒填：地址、截標日期」

### ★★ 唯一鍵是三欄

`unique (source, url, title)`，而 `url` 是 `not null default ''`。

- **含 `title`**：郵局那一支「無各別標案頁，連結統一指向來源頁」—— 每一筆 url 都一樣。
  少了 title 那 83 筆會互相覆蓋，而且是安靜的
- **`url` 不可為 null**：`coalesce(url,'')` 是運算式索引，`ON CONFLICT` 推不出來
  （9.1② 那件事，踩過兩次）

### 只收「有推播的」

爬蟲的白名單／黑名單寫死在 `scraper.py` 的 `SOURCES`。
**這代表爬蟲的篩選條件就是 ERP 的篩選條件** —— 哪天調了關鍵字，
這邊的數量會安靜地跟著變。所以每筆都記 `run_at`，查得出是哪天開始的。

## 9.1 最貴的五個（都跟「不報錯」有關）

### ① RLS 擋下的寫入 → 回成功且影響 0 列 🔴🔴

**2026-08-19，賠掉一整天。**

PostgREST 遇到 RLS 擋下的 `UPDATE` / `DELETE` **不會報錯**，只回一個空陣列。

```ts
// ❌ 錯的
const { error } = await supabase.from('x').update(patch).eq('id', id);
if (error) return flash('失敗');
flash('已儲存');          // ← 一列都沒改，而畫面說成功了

// ✅ 對的
const { data, error } = await supabase.from('x').update(patch).eq('id', id).select('id');
if (error) return setErr('儲存失敗：' + error.message);
if (!data?.length) return setErr('沒有任何一列被更新，通常是權限或狀態已經變了。');
```

**症狀**：使用者說「按了沒反應」或「存了但重整就沒了」。
**現在的做法**：所有寫入都 `.select('id')` 檢查長度。

### ② `ON CONFLICT` 對不到部分索引 🔴🔴 **踩過兩次**

**第一次** 2026-08-19（migration 150/151/152）—— 主管按不動「確認付款日」，查了一整天。
**第二次** 2026-08-22（migration 164/165）—— 收款手續費存不進去。**同一天內又犯一次。**

```sql
-- ❌ 部分索引，ON CONFLICT 推不出來
create unique index x_uidx on t (col) where col is not null;

-- ✅ 完整索引。NULL 之間不算相等，所以效果一樣
create unique index x_uidx on t (col);
```

**症狀**：`there is no unique or exclusion constraint matching the ON CONFLICT specification`
**為什麼會犯第二次**：164 的自檢只用 `select` 確認「索引存在嗎」—— 索引**確實存在**、名字對、一切看起來都好。

> **教訓**：驗證段要有**真的寫入**（見 9.4）。

### ③ 觸發器一律覆寫，把手選的值蓋掉 🔴

**2026-08-22。** `sync_order_account()` 每次寫入都 `new.account_code := order_account_code(...)`。
愛皮的「團費收入」被改成「租金收入」，然後被另一道防線擋下 —— **功能完全存不進去**。

**症狀**：新功能第一天就是壞的，而錯誤訊息是另一件事（「科目不屬於這一本帳」）。
**修法**：`migration_163` 讓它 `if book <> 'anxing' then return new`。
**教訓**：加新的資料路徑之前，先查**有沒有觸發器在覆寫那一欄**。

### ④ `WHEN (new.…)` 不能用在含 DELETE 的觸發器上 🔴

**2026-08-22。** 我原本要給認列觸發器加條件：

```sql
-- ❌ DELETE 時 new 是 null，而且會把 DELETE 那條路弄丟
create trigger t after insert or delete or update on orders
  for each row when (new.book = 'anxing') execute function f();

-- ✅ 拆成兩支
create trigger t     after insert or update on orders
  for each row when (new.book = 'anxing') execute function f();
create trigger t_del after delete on orders
  for each row execute function f();      -- 清理無條件跑
```

**如果當初沒發現**：刪掉訂單後認列紀錄留在表裡，**營收表繼續算那筆錢** —— 不報錯，只有月營收莫名變高。

### ⑥ 註解裡的一個星號，讓一支 migration 假裝跑過了三天 🔴🔴 **（2026-08-24）**

`migration_171` 貼進 SQL Editor 就報 `unterminated /* comment`。原因是 **Postgres 的區塊註解可以巢狀**，而我在註解裡寫了 Markdown 粗體：

那裡開了一層巢狀註解，我的 `*/` 只關掉內層，外層一路吃到檔尾。

## 9.2 資料庫

| 坑 | 症狀 | 對策 |
|---|---|---|
| Supabase 預設**最多回 1000 列且不報錯** | 要加總的查詢在第 1001 筆之後安靜消失 | `lib/fetch-all` 的 `fetchAll()` |
| `now()` 是**交易開始時間** | 同一交易裡呼叫兩次結果相同 | 要真的「現在」用 `clock_timestamp()` |
| `information_schema.columns` 沒帶 `table_schema='public'` | `properties`、`attachments` 這種名字在別的 schema 也有，自檢誤報 | 一律帶 `table_schema='public'` |
| SQL Editor 把整份腳本包在**一個交易**裡 | 任一錯誤全部回滾 | 會失敗的東西（建索引、裝擴充）用 `exception` 包 |
| SQL Editor **只顯示最後一個 SELECT** | migration 自檢寫兩個 SELECT，前面那個永遠看不到 | 自檢一律**單一 SELECT** ＋ `union all` |
| **Postgres 的區塊註解可以巢狀** 🔴🔴 | 註解裡寫 `` **只有 pr/** `` → `pr` 後的斜線碰上粗體星號 = `/*` 又開一層 → `unterminated /* comment`，**整份不執行**（2026-08-24） | 前綴後面不要緊接 `**`。用反引號寫成 `` `pr/` ``。已由 `sql-comments.test.ts` 自動擋 |
| PostgREST 批次 upsert 取**欄位聯集** | 某列少了鍵會被填 null | 必須明寫回舊值 |
| `min(uuid)` 不存在 | | 用 `(array_agg(id))[1]` |
| enum 的 `ALTER TYPE ... ADD VALUE` **不能在交易裡跑** | 那支腳本整份失敗 | 用 `text` ＋ CHECK |
| `CREATE OR REPLACE FUNCTION` **不能改參數名** | | 換名字要先 DROP |
| BEFORE 觸發器**按名字字母序**跑 | 順序依賴時會靜默失效 | 依賴順序要寫進註解（`trg_orders_account` < `trg_orders_book_code` 是巧合） |
| **欄位有 FK、有索引、前端在讀，但從來沒有人寫過它** 🔴 | `expenses.request_id` 一直是 null，支出頁的憑證圖片永遠寫「尚未上傳」（migration_169，2026-08-24） | 見下 |
| **衍生資料表不能直接改** 🟠 | 回填 `customers.name` 被 `customers_guard()` 擋下，整份 migration 回滾（migration_173，2026-08-24） | 改**源頭**（`orders.guest_name` / `contracts.tenant_name`），再呼叫 `sync_customers()` 重算。衍生表也不要掛正規化觸發器 —— 會跟守衛打架 |
| **刪掉一個 CTE，忘了刪它前面的逗號** 🟠 | `syntax error at or near "into"`，整份不執行。中間隔著十幾行註解所以看不出來（migration_173，2026-08-24） | 已由 `sql-comments.test.ts` 的 `danglingCteComma` 自動擋（只掃 `supabase/migrations`） |

**★ 關於最後一條**：`gen_expenses_from_pr()` 的 insert 欄位清單裡沒有 `request_id`，
而 `expenses_request_id_fkey` 與 `exp_request_idx` 都在、前端 `inheritFromRequestId={d.request_id}` 也在。
**每一個零件單獨看都正確**，串起來就是一句「尚未上傳」—— 沒有紅字、沒有錯誤，
而那句話看起來完全合理。查了才知道那條路從來沒有走通過。

判斷方法：**看到「空的但合理」的畫面，先去查那個欄位有幾筆非 null**，
不要先查前端。`select count(*) from t where col is not null` 回 0 就是答案。

補救用**觸發器**而不是改產生資料的函式 —— 往 `expenses` 塞資料的函式有兩支，
其中「匯款手續費」那支的定義不在 repo 裡（見 README 9.5）。
觸發器只寫一個欄位，兩支都涵蓋，而且不必重寫任何手上定義可能過時的東西。

| **只用 `title` 當說明** 🟠 | 手機沒有 hover，那句話等於不存在。而且 `title` 放不下「檢查什麼」，只放得下「會檢查」。要說明就做成看得到的 ⓘ |
| **猜欄位名／表名，猜錯了畫面完全正常** 🔴 | 條件式永遠不成立，那段 UI 一次都沒出現過。使用者連按三次重新整理都一樣，而**沒有任何錯誤**（2026-08-24，同一天三次） |

**★ 關於最後一條**——同一天犯了三次，三次都是「沒查證就寫」：

| 我寫的 | 實際 | 症狀 |
|---|---|---|
| `it.code === '對不到房源'` | 那個標籤是 **`it.field`** | 提示一次都沒出現 |
| `from('airbnb_listings')` | 表名是 **`property_listings`** | 查詢報錯 |
| `sync_issue_log.listing_id` | **那個欄位不存在** | 差點回一個假的「以前沒出現過」 |

**判斷方法**：要用某個欄位之前，先 grep 它在別的地方怎麼被讀的
（`ISSUE_ADVICE[field]`、`.select('…')`、type 定義），不要從標籤文字反推欄位名。

**補救**：把條件抽成 `.ts` 的純函式（例如 `needsCrawlerDetail(field)`），
寫在 `.tsx` 裡的判斷式**測試環境不處理 JSX、測不到** ——
抽出來之後改錯了會紅，不會安靜地什麼都不顯示。

## 9.4 寫 migration 的規矩（都是踩出來的）

1. **結尾補 `select record_migration('編號_名稱')`**
2. **自檢只能有一個 SELECT** —— SQL Editor 只顯示最後一個
3. **★ 驗證段要有真的寫入，不能只有 `select`**
   - `sync_order_deposits()` 的陣列 bug 撐了兩天，因為驗證只讀不寫
   - migration_164 的部分索引問題也是這樣漏掉的
   - 做法：包在 `do $$ … $$` 裡寫一次、檢查、再 raise 讓它回滾
4. **要能重跑** —— 「已完成」要跳過而不是中止（`migration_63` 的教訓）
5. **覆寫整支函式時，逐段對照線上定義** —— 不要照 `schema-baseline.sql`（見下）
6. **既有行為要有一項自檢守著** —— 「N / N 全等」比「✅」有用
7. **★★ SQL Editor 沒有登入身分 —— 凡是看 `auth.uid()` 的東西都測不到** 🔴 **（2026-08-22，migration_167）**

   `current_role_of()` 的定義是 `select role from profiles where id = auth.uid() and active`。
   SQL Editor 是 `postgres` 連線，`auth.uid()` 是 **null**。所以：

   | 寫在自檢裡的東西 | 在 SQL Editor 跑出來 |
   |---|---|
   | `trash_can_delete('orders')` | **永遠 false** |
   | 任何 RLS 政策的 `using` | 永遠不成立 |
   | `soft_delete(...)` | **第一行就回 NO_PERM，一列都沒動** |

   167 把 `case when trash_can_delete('orders') then '✅' else '❌' end` 寫成驗收標準，
   **那一項每次都會是 ❌，跟這支 migration 改了什麼完全無關。**
   更糟的是同一支還有一個「真的刪一筆」的 `do` 區塊 —— 它也走到 NO_PERM 就結束，
   而結果印在 `raise notice`，**SQL Editor 看不到**。
   兩個問題剛好互相遮蓋：沒測到東西，也沒有人知道沒測到。

   **要測角色相關的行為，必須假扮身分**：

   ```sql
   -- true = local，交易結束自動還原
   perform set_config('request.jwt.claims',
                      json_build_object('sub', 某人的_uuid::text)::text, true);
   -- 現在 auth.uid() 就是那個人，current_role_of() 查得到角色
   ```

   - **不要 `set role authenticated`** —— 切了之後自檢自己查 `profiles` 會被 RLS 擋。
     `current_role_of()` 是 SECURITY DEFINER，只看 `auth.uid()`，不需要切。
   - **假扮失敗時要顯示「⚠ 測不出來」，不能顯示 ❌。**
     把「沒測到」報成「壞掉」比不報還糟 —— 會有人去修一個沒壞的東西。
   - 完整範例：`migration_168_verify_delete_perm.sql`（純驗證，一個字都沒改）。

8. **★ 「函式定義裡有沒有這段字串」不等於「行為對不對」** 🟠

   `pg_get_functiondef(...) like '%housekeeper%'` 只證明**字打對了**。
   跟 9.1② 是同一種錯覺：索引存在、名字對、形狀都好，而 `ON CONFLICT` 就是對不到。
   比字串可以當**輔助**，不能當唯一的驗收。

9. **★ 自檢的 exception handler 要抓 `others`，不要只抓自己丟的那一種** 🟠

   用 `raise exception … errcode='restrict_violation'` 回滾測試資料時，
   若只寫 `exception when restrict_violation`，被測的觸發器丟出來的
   `check_violation` 會**炸掉整份腳本**，症狀是「跑 migration 出現一句看不懂的錯」。
   自檢不該比被檢查的東西還脆弱。

10. **★ plpgsql 內層 `begin/exception` 是隱式 savepoint —— 資料回滾，變數留著**

    這是「真的寫入 ＋ 回滾 ＋ 結果看得到」唯一乾淨的做法：
    在內層把結果存進變數 → `raise` 回滾 → 出了內層再 `insert into` temp table。
    直接在最外層 raise 的話，連 temp table 的內容都會一起消失。

11. **★ 不要把 `set_config` 跟被測的函式放在同一個 SELECT 的不同欄位**

    Postgres **不保證欄位的求值順序**。可能先問完權限才換身分，
    那樣每一列都是上一個人的答案，而且看起來完全正常。用 plpgsql 迴圈逐筆做。

12. **★★ 自檢的條件不能複製「被檢查的那段邏輯」** 🔴 **（2026-08-24，migration_174）**

    174 要刪掉舊的唯一索引，清理條件是：

    ```sql
    where indexdef like '%contract_id%currency%' and indexdef not like '%kind%'
    ```

    自檢那一項**用了一模一樣的條件**去問「舊索引清乾淨了嗎」——
    於是回了 ✅，而實際上有一顆 `dep_contract_once_idx`
    （單欄、**不含 currency**）還在，訂金一存就撞上去。

    **用同一個條件檢查自己做過的事，永遠會通過。** 漏網的兩邊都看不到。

    這跟 167 那次是同一種錯（自檢問了一個恆為真／恆為假的問題）：

    | | 清理／動作用的條件 | 自檢該問的 |
    |---|---|---|
    | ❌ | `indexdef like '…currency…'` | 同一句話 |
    | ✅ | 同上 | **「還有幾顆唯一索引提到 contract_id 卻沒提到 kind」** |

    **自檢要問結果，不要問過程。** 問結果的話，不管它叫什麼名字、
    欄位怎麼組合，都逃不掉。

---

13. **★★★ 自檢不要寫死數量 —— 寫下限，並印出實際值** 🔴 **（2026-08-28，一天內三次）**

    | 寫成 | 什麼時候紅 | 紅的原因 |
    |---|---|---|
    | `scanned > 10`（sql-comments） | 封存 migration 之後活躍目錄剩 8 支 | 跟 SQL 對不對無關 |
    | `stops.length >= 5`（day-phase） | 漸層從九停簡化成三停 | 跟可讀性無關 |
    | `= 7`（migration_180 的 parent 數） | 多加一欄變成 8 | 印出「❌ 只有 8 / 7」這種看不懂的句子 |

    三次都是**把「現在剛好是幾個」寫成了規則**。

    ★★ 而三次紅燈的原因都跟被檢查的東西無關 —— 那是**假警報**。
    假警報比漏報更傷：它會讓人去修一個沒壞的東西，
    而下一次真的紅的時候，就沒有人相信了。

    **做法**：

    ```sql
    -- ❌ 把此刻的數量當規則
    case when n = 7 then '✅' else '❌ 只有 ' || n || ' / 7' end

    -- ✅ 下限 ＋ 印出實際值。多了是有人加了新東西,那是好事
    case when n >= 8 then '✅ ' || n || ' 個' else '❌ 只有 ' || n || ' 個，少了' end
    ```

    ★ 下限的意義是「這個守門員還有沒有在守東西」，不是在數數。

## 9.5 ⚠ `schema-baseline.sql` 不可信

**2026-08-22 一天之內錯了五次**，其中兩次差點寫出錯的 migration：

| # | 錯在哪 |
|---|---|
| 1 | 少 `order_payments` 整張表 |
| 2 | 少 `deposits.lines` |
| 3 | `gen_expenses_from_pr` 多了一段線上**沒有**的日期連動 |
| 4 | `att_one_parent` 少兩個 parent 欄位 |
| 5 | 少 `orders.account_code`（而且它有 4948 筆資料） |

**要動觸發器或函式之前，一律先問線上：**

```sql
select pg_get_functiondef(p.oid)
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public' and p.proname = '<函式名>';
```

**該做的事**：跑一次 `pg_dump --schema-only` 重生 baseline。十分鐘的事，不做的話下一個人還會再撞。

## 9.6 一句話總結

**這個專案的錯誤幾乎都是「安靜」的。**

不是崩潰、不是紅字，而是：

- 一列沒改，而畫面說成功了
- 一筆錢沒算進去，而總額看起來很合理
- 一顆按鈕沒反應，而沒有任何訊息
- 查詢的區間反了，而畫面老實地回答「$0」
- 一支函式測試全綠，而從來沒有任何畫面呼叫過它

所以**每一個寫入都要問「改到幾列」，每一個擋阻都要說出原因，每一個自檢都要真的寫一次**。

# 十、介面規則（2026-08-29 統一）

## 10.1 這件事的起點

盤點時**卡片容器有 87 種寫法**。同一種東西在三頁長得完全不同：契約用實心藍底、
暫收也是實心藍底但小一號、帳戶是淺藍底加外框。

不是誰寫錯了 —— 是**沒有一個地方可以定義「卡片長什麼樣」**。

**★★★ 這種不一致 `tsc` 與測試都抓不到。** class 打錯不會報錯，只會變醜。
所以唯一的防線是流程：**先找有沒有現成的元件，沒有才新增，而且新增在共用的地方。**

```bash
ls src/components/                     # 共用元件
grep -n "^  \." src/app/globals.css   # 元件層的 class
```

## 10.2 共用元件（動手前先看這張表）

| 元件 | 管什麼 | 全站幾處在用 |
|---|---|---|
| `components/StatHero.tsx` | 深藍大卡（一頁最重要的那個數字） | 6 |
| `components/BarList.tsx` | 分項面板（項目 ＋ 長條 ＋ 數字） | 10 |
| `components/StatCard.tsx` | 一排統計小卡 | 多處 |

| `lib/sortable.tsx` | 可排序表頭 `SortTh` | 多處 |

長出一個 prop」，最後才考慮新增。** 直接在頁面裡手寫 —— 那就是第 88 種。

## 10.3 六條最常被違反的

**① 字級分兩套尺度：外框 vs 資料。**
控制項與按鈕、卡片標題用 `text-ui`（17px）；欄位小標題、附註用 `text-uisub`（15px）；
**表格內文維持 Tailwind 預設的 `text-sm` / `text-xs`**。
2026-08-29 那次把 `text-xs`/`text-sm` 全域 +2px —— 那兩個 class 用了 1,438 次、
幾乎全是表格內文，結果是欄位一多就換行，而**換行的表格比小一點的字難讀得多**。

**② 對齊靠固定高度，不是調 padding。**
`select`（有下拉箭頭）、`input`、`button` 用同樣的 padding 算出來的高度天生就不同，
而且會隨字級與瀏覽器再變一次。規則寫在 `globals.css` 的 `.filter-bar`：
**48px（手機）/ 40px（桌機）**，新欄位放進去就自動是對的。

**③ 篩選是「看哪些」、動作是「做什麼」、模式是「用哪種眼光看」——三種東西三個位置。**
篩選在白卡裡、動作在卡片外面另起一行靠右、模式開關在標題列右上。
混在一起的話「+ 新增」看起來像第七個篩選欄位，而**手機上篩選是收起來的**，
放在裡面的東西會跟著被收走。

**④ 捲軸的門檻是「它是主體還是提醒」。**
分項面板、欠款、待開發票、稽核清單這種**摘要**露約九到十列就捲；
那一頁的**主清單**不限、整頁捲。四列太少（看不出分布），全展開會把主體推出畫面。

**⑤ 名字放不下就換行，不要 `truncate`。**
帳戶叫「(安幸)元大 20992…」，四個帳戶共用前六個字 —— 截斷砍掉的正好是唯一分得
出來的那一段。這跟 `splitTail` 要留末五碼是同一條道理：**差異在尾巴。**

**⑥ 顏色有語意，不能隨手拿來配色。**
綠＝已收／通過、藍＝主色與押金、琥珀＝訂金與重要、紅＝警示或會計的借貸方向、
紫＝非營運。**借用任何一個都會讓那個顏色失去原本的意思。**
配色的細節（對比度門檻、深底與白底要兩套色）在
[`.claude/skills/anxing-color/SKILL.md`](.claude/skills/anxing-color/SKILL.md)。

## 10.4 ★★★ UI 改版一律先過審

**動到畫面長相的事，先給看、等一句「做」，才可以改檔案。**
適用範圍、怎麼給看、什麼情況不用過審，寫在 [`CLAUDE.md`](CLAUDE.md)。

# 十二、`supabase/` 底下的三個資料夾（2026-09-02 整理）

## 12.1 為什麼要分開

**`audits/` 是 2026-09-02 建的**，把兩批唯讀查詢收在一起:
原本混在 `migrations/` 的 16 支 `audit_*.sql`，加上散在 `supabase/` 根目錄的 9 支 `查-*.sql`。

`deploy.ps1` 推完會列出「還沒跑的 migration」，而它認的是
`supabase/migrations/*.sql` 這個路徑 —— 唯讀的稽核查詢混在裡面，
每次推送都會被列成「還沒跑」，而它們**根本不需要跑**。

★ 那種假警報的成本不是麻煩，是**下次真的有 migration 要跑時沒有人細看**。

## 12.2 什麼時候封存

**一支 migration 跑完、而且線上穩定幾天之後**，搬進 `archive/migrations-N-M/`。

★ `deploy.ps1` 只算 git 狀態是 `A`（新增）的檔案，所以**搬走不會被誤算**
（那段的註解寫著:「封存一次 70 支就會跳出『這次帶了 70 支 migration』，
而那個數字一旦不可信，下次真的有 3 支要跑的時候也不會有人細看」）。

## 12.3 封存**不是**刪除

那些檔案是**唯一**寫著「當初為什麼這樣改」的地方 ——
`schema-baseline.sql` 是 dump，它只有結果沒有理由，而且會過期
（2026-09-02 連踩兩次:`hk_task` 整張表與五條 `_read` policy 都不在裡面）。

★ 要查一支函式現在長怎樣，**用 `pg_get_functiondef()` 問資料庫**，
不要翻 archive 也不要翻 baseline。

# 十三、備份與還原

> 2026-08-31 加。在這之前**沒有任何備份** —— 資料庫掛掉、誤刪一張表、
> 或 migration 寫錯把某一欄清空，都沒有東西可以回去。

## 13.1 三條路，兩個地方

|  | GitHub（自動） | 本機（自動下載） | 本機（手動 dump） |
|---|---|---|---|
| 腳本 | `.github/workflows/backup.yml` | `scripts/fetch-backup.ps1` | `scripts/backup-db.ps1` |
| 什麼時候 | 每天台灣 04:00 | 每次登入後 3 分鐘 | 你按的時候 |
| 做什麼 | 連資料庫 dump | **下載 GitHub 那份** | 連資料庫 dump |
| 產出 | `anxing.sql.gz` ＋ `auth.sql.gz` | 同左（原封不動搬回來） | `anxing_日期.sql` |
| 涵蓋 auth | ✅ 盡力而為 | ✅ 跟著來 | ❌ 沒有 |
| 放哪 | Actions 的 artifact | `~\anxing-db-backup\gh_日期_runNNN\` | `~\anxing-db-backup\` |
| 保留 | 30 天（GitHub 刪） | 30 天（腳本刪） | 30 天（腳本刪） |
| 要裝什麼 | 不用 | `gh`（裝一次 ＋ 登入一次） | `pg_dump`（裝一次） |

### 為什麼是這個組合

**GitHub 那支是主力。** 每天自動，人不用記得。

**「下載」是把雲端那份搬回自己手上。** 不是再 dump 一次 ——
少拉一次全量資料，而且本機那份跟雲端**保證是同一批 bytes**。
各自 dump 的話兩份差幾分鐘，出事時還要比對「哪一份比較新」。

**「手動 dump」留著給兩種情況**：
「等一下要跑一支會改資料的 migration，我現在就要一份」，
以及「GitHub 那邊今天沒跑成功」。★ 備份系統最不該有的就是單一路徑。

### ★★ 三支都會先驗證再收工

檔案太小、或四張主表（`bank_transactions` / `orders` / `expenses` / `contracts`）
的 `COPY` 段找不到，就當作失敗 —— 不會靜靜留下一個看起來像備份的空檔。

> 2026-08-31 這道檢查**真的擋下了一次**。第一版 workflow 用 `supabase db dump`，
> 跑完是綠的、檔案也產生了，但 `roles.sql` 只有 297 bytes、`data.sql` 裡
> 一張業務表都沒有 —— **它成功地備份了空氣**。
> 只看「Actions 綠了」的話，會以為有備份，而三十天後打開來是空的。

★ 下載那支**還會再驗一次**，即使 workflow 已經驗過。
中間隔了一次網路傳輸與一次解壓縮，任何一段壞掉都會留下大小正常、內容是垃圾的檔案。
「上游驗過了所以這裡不用驗」是備份系統最常見的漏洞：
每一段都相信上一段，於是沒有人真的看過最後那個檔案。

### ★ 太舊會出聲

下載那支發現「最新的備份已經超過 2 天」時會警告。
排程壞掉的症狀是**每天都下載成功** —— 下載的是同一份三個禮拜前的東西，
而畫面上每天都是綠的。

## 13.2 第一次要設定的東西

### GitHub（設一次，之後全自動）

1. **先確認 repo 是 private。**
   ★★★ artifact 的下載權限跟 repo 一樣 —— repo 是 public 的話，
   任何人點一下就下載到整個資料庫，而**不會有任何警告**。
   repo 首頁標題旁邊要看到灰色的「Private」標籤。

2. Supabase Dashboard → 右上角 **Connect** → **Session pooler**，
   複製那串 `postgresql://...`，把 `[YOUR-PASSWORD]` 換成資料庫密碼。

3. GitHub → repo → Settings → Secrets and variables → Actions →
   New repository secret：

   | | |
   |---|---|
   | Name | `SUPABASE_DB_URL` |
   | Secret | 上一步那串字 |

4. Actions 頁籤 → 「每日資料庫備份」→ **Run workflow** 手動跑一次，
   確認會綠。★ 不要等明天 —— 設錯了要今天知道。

### 本機的自動下載（設一次）

1. 裝 GitHub CLI 並登入：

```powershell
winget install --id GitHub.cli
# 裝完重開 PowerShell
gh auth login          # 選 GitHub.com → HTTPS → 用瀏覽器登入
```

2. 登記成登入時自動跑（**只要跑一次**）：

```powershell
cd C:\Users\ASUS\Desktop\anxing-web
.\scripts\register-backup-task.ps1
```

3. 馬上試一次，不用等重開機：

```powershell
Start-ScheduledTask -TaskName AnxingBackupFetch
```

紀錄在 `~\anxing-db-backup\fetch.log`。不想要了：

```powershell
Unregister-ScheduledTask -TaskName AnxingBackupFetch -Confirm:$false
```

### 本機的手動 dump（設一次）

1. 裝 `pg_dump`：<https://www.postgresql.org/download/windows/>
   安裝時**只勾 Command Line Tools**（資料庫本體幾百 MB，用不到）。

2. 記住連線字串（只跑一次，會永久記住）：

```powershell
[Environment]::SetEnvironmentVariable('SUPABASE_DB_URL', '貼在這裡', 'User')
```

3. 關掉 PowerShell 重開，然後：

```powershell
cd C:\Users\ASUS\Desktop\anxing-web
.\scripts\backup-db.ps1
```

★ 那串連線字串裡有**資料庫密碼**。不要貼進聊天室、不要 commit、
不要傳給任何人（包含 Claude）—— 它等於整個資料庫的鑰匙。

## 13.3 ★★★ 沒有驗證的備份不算備份

兩支腳本都會在匯出後**檢查檔案裡真的有資料**：

* 檔案大小要超過門檻（`pg_dump` 權限不足時會回 0 但只寫出檔頭）
* `data.sql` 裡要找得到 `bank_transactions` / `orders` / `expenses` / `contracts`

找不到就**讓它失敗**，不會靜靜上傳一個空的 artifact。

> 這一條是從對帳單那次學到的：`groupRows` 的測試 57 條全綠，
> 線上 56 筆帳號無聲消失 —— 因為測試素材只有一種來源。
> 備份是同一種形狀的風險：**成功的訊息不等於成功的結果。**

★ 每季自己還原一次到一個測試專案。從來沒還原過的備份，
只是一個沒有人開過的檔案。

## 13.4 還原

### 完整還原（GitHub 那三份）

1. 到 Actions → 那次執行 → 下載 `db-backup-xxx.zip`，解壓、`gunzip`
2. 建一個新的 Supabase 專案，拿它的連線字串
3. **順序不能換**（roles 要在 schema 之前，schema 要在 data 之前）：

```bash
psql \
  --single-transaction \
  --variable ON_ERROR_STOP=1 \
  --file roles.sql \
  --file schema.sql \
  --command 'SET session_replication_role = replica' \
  --file data.sql \
  --dbname "新專案的連線字串"
```

★★ `session_replication_role = replica` 是**關掉觸發器**。
沒有它的話，還原 `bank_transactions` 時會一列一列去撞
`trg_bank_txn_memo_only`（migration_166），整份還原失敗。

### 只救幾張表（本機那一份）

整份還原太大動作時，用文字編輯器打開 `anxing_日期.sql`，
找到那張表的 `COPY public."xxx" ...` 到 `\.` 為止那一段，貼進 SQL Editor。

★ 先把現有的那張表清空或改名，不然會撞主鍵。

### 常見錯誤

| 訊息 | 怎麼辦 |
|---|---|
| `permission denied to grant role "postgres"` | 打開 `roles.sql`，把含 `cli_login_postgres` 的那行註解掉 |
| `ALTER ... OWNER TO "supabase_admin"` 權限錯誤 | 打開 `schema.sql`，把那幾行註解掉 |
| `role "xxx" does not exist` | roles.sql 沒跑或跑在 schema 之後 —— 順序不能換 |

## 13.5 備份**沒有**涵蓋的東西

★★ 這幾樣還原不回來，出事時要手動重建：

* **Vercel／Vultr 的環境變數** —— 抄一份存在密碼管理器裡
* **Supabase 的 Auth 設定**（第三方登入、email 模板）
* **Database Webhooks 與 Publications** —— 還原後要去 Dashboard 重新啟用
* **Storage 裡的檔案本體** —— `storage.objects` 那張表備份得到，
  但**檔案內容存在 S3，不在資料庫裡**。要另外搬（見 Supabase 官方文件的
  migrating storage objects 那一節）
