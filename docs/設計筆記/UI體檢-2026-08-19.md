# 全站 UI 體檢（2026-08-19）

這份是**量出來的**，不是憑印象。每一條都附了怎麼量的，你可以自己重跑一次。

前提要講清楚：我讀的是程式碼，不是每一頁的實際畫面。所以「版面醜不醜」我判斷不了，
這裡列的全是**結構性的問題** —— 那種會反覆在每一頁重演、而且會慢慢變貴的。

---

## P0　六頁在手機上只有桌機表格

```bash
for f in src/app/\(app\)/*/page.tsx; do
  t=$(grep -c "<table" "$f"); [ "$t" = "0" ] && continue
  m=$(grep -c "md:hidden" "$f"); [ "$m" != "0" ] && continue
  basename $(dirname $f)
done
```

| 頁 | 手機上的狀況 |
|---|---|
| `shortterm` 短租訂單 | 只有橫向捲動的表格 |
| `expenses` 支出明細 | 同上 |
| `revenues` 營收表 | 同上 |
| `reviews` 房源評價 | 同上（**今天已經踩到過**） |
| `accounts` 帳戶明細 | 同上 |
| `admin` 權限管理 | 同上，九張表 |

有手機版面的：`purchases`（4 處）、`cleaning`（3）、`contracts` / `customers` / `dashboard` / `deposits`（各 1）。

**為什麼這是 P0**：今天你在手機上看房源評價，第一個反應是「讀不出來」。
那次的根因是載入時序，但**你會用手機看這幾頁**這件事已經被證實了。
橫向捲動的表格在手機上等於「看得到但用不了」。

**建議做法**：不要每頁各寫一套。先做一個 `<CardList>`，
接受「主要欄位／次要欄位／右側動作」三個 slot，六頁共用。
一頁一頁改的話，第三頁就會開始長得不一樣。

## P1　十一個表格的欄寬是瀏覽器自己分配的

```bash
grep -c "table-fixed" src/app/\(app\)/*/page.tsx
```

只有 `accounts` 有（而且是今天才加的）。其他每一張表都是 `table-auto` ——
**誰的字多誰就寬**。

今天在帳戶明細踩到的就是這個：摘要欄有一串
`4010054659 代繳市水 08025 112 TPCW`，把寬度吃掉，
而真正要看的交易帳號被擠到折成三行。**佔最多版面的是最不重要的那一欄。**

同樣的事會在每一張表重演，只是還沒有人抱怨到。最可能的下一個：
`purchases` 的請款事由、`expenses` 的品項、`contracts` 的房客名。

**建議做法**：抽一個 `<DataTable cols={[...]}>`，
內部就是 `table-fixed` ＋ `colgroup` ＋ `min-w`，
欄寬變成呼叫端的一個數字。順便把三件事一次做對：
金額欄 `whitespace-nowrap`、長文字欄 `break-words`、窄螢幕橫捲而不是等比壓縮。

## P1　輸入框有十種寫法

```bash
grep -rhoE "bg-white rounded-lg border border-mor-line px-2[^\"]*" src/ | sort | uniq -c | sort -rn
```

```
9  … px-2 md:py-1.5 disabled:bg-gray-50
4  … px-2 text-sm
4  … px-2 md:py-1.5
2  … px-2 md:py-1.5 text-right disabled:bg-gray-50
1  … px-2 py-2 h-24 md:h-16 disabled:bg-gray-50
… 另外五種
```

彈窗外框四種：

```
4  fixed inset-0 … items-stretch md:items-start … overflow-auto md:py-10
4  fixed inset-0 … items-center justify-center            ← 手機上不會升起
2  fixed inset-0 … items-stretch md:items-center …
1  fixed inset-0 … items-start … py-10
```

**症狀不是「醜」，是「改一次要改十處」**，而且漏掉的那幾處不會報錯 ——
只會在某一頁的某個欄位上留下一個手機按不到的 32px 輸入框。

第二種彈窗寫法（`items-center`）在手機上是置中小框，
跟另外六個「從底部升起的整頁面板」行為不同。同一個 App 裡兩種彈窗，
使用者每次都要重新判斷「這個能不能往下捲」。

**建議做法**：`<Field label>` ＋ `<Modal>` 兩個元件。
不用大改，把既有的 class 字串搬進去就好。

## P2　四個檔案超過 1,600 行

```
purchases  2,275
contracts  2,004
admin      1,881
deposits   1,623
shortterm  1,315
dashboard  1,200
```

真正的代價不是難讀，是**判斷邏輯困在 `.tsx` 裡就測不到**
（測試環境不處理 JSX）。這是 `CLAUDE.md` 已經寫下的規矩，
但這幾個檔案是規矩訂之前長出來的。

目前抽出去的：`order-payment` / `deposit-payment` / `deposit-transfer` /
`bank-filter` / `bank-statement` / `estate-manager` / `fee-types` / `sortable` —— 這些都有測試。
還留在 `.tsx` 裡的：請款單的狀態流轉、契約的期數計算、儀表板的比較期。

**建議做法**：不要為了行數而拆。**只在下次要改那一頁時**，
把那次碰到的判斷式順手搬出去並補測試。硬拆一輪的風險比收益大。

## P3　空狀態與提示文案各寫各的

「沒有符合條件的紀錄」「沒有符合的資料」「尚未有收款紀錄」「這一類目前沒有押金紀錄」
——意思一樣，寫法都不同。

這個影響最小，但它是**最便宜**的一項：統一之後，
使用者掃過去就知道「空的」跟「篩掉了」是兩件事。
（帳戶明細與押金頁已經分開講了，其他頁還沒。）

## 已經做對、不要弄壞的

- **色票**：`mor-slate` 90 次、`border-mor-line` 438 次 —— 全站一致，別引進新顏色
- **共用元件覆蓋率不差**：`SortTh` / `FilterToggle` / `Req` / `ExportButton` 各 7 頁
- **金額一律千分位**、日期一律帶年份
- **「還在載」跟「沒有資料」分開講** —— 押金頁與評價頁做對了，值得推廣到其他頁

---

## 建議順序

1. `<CardList>` ＋ 先套 `reviews` 與 `shortterm`（手機上最常看的兩頁）
2. `<DataTable>` ＋ 先套 `purchases` 與 `expenses`（欄位最多的兩頁）
3. `<Field>` ＋ `<Modal>`，隨著上面兩步順手替換
4. 文案統一

**一次做一項，每一項都能單獨推。** 一次全改的話，出問題時分不出是哪一項造成的。
