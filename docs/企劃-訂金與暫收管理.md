# 企劃：訂金功能 ＋ 押金管理改名為「暫收管理」

> 2026-08-24　使用者提出　**這份是企劃，還沒有寫任何程式碼**

---

## 一、需求原文

> 幫我設計一個訂金功能。在押金下方打勾後，契約只要填 物業、房源、姓名，其他不用填。
>
> 步驟：收訂金 → 知道契約內容 → 收押金餘款 → 然後租約開始收房租
>
> 押金管理改叫「暫收管理」，含訂金與押金。
>
> 契約輸入完訂金後 → 變「未付訂金」→ 訂金收款 → 訂金退款。流程參照押金製作。
> 訂金退款一樣兩票制，按退款會到請款審核，像押金一樣退款。
>
> 之後契約輸入押金後，可以把訂金轉移到押金 → 如果全收變「已收押金」，
> 或是部分收款（參考押金移房設計）。訂金轉移後狀態變「已退｜轉押」。

**2026-08-24 補充（改了原本的決定）：**

> 訂金還是做一個沒收訂金好了。訂金檢視頁按了會變一次性收入，
> 項目「取消入住」，會計科目 ~~違約金~~ → **「其他」**（2026-08-24 再次修正）。
>
> 訂金第三階段改成 **沒收 / 退款 / 轉押金**。
>
> 因此卡片有兩列：一列給訂金，一列給押金。

## 三、⚠ 五個必須先解決的技術障礙

**這一節是這份企劃真正的內容。** 需求本身不難，難的是它踩到五個既有機制。
每一個都不會報錯 —— 只會安靜地算錯。

### ① `deposits` 一張契約只能有一列（唯一索引）

`sync_contract_deposits()`（migration_56）：

```sql
on conflict (contract_id, currency) where contract_id is not null
```

**同一張契約同時有訂金與押金 = 兩列 deposits = 撞上這個唯一索引。**

→ 索引必須改成 `(contract_id, currency, kind)`。
→ ⚠ 這是**部分索引**（`where contract_id is not null`）。
   README 9.1② 記著：`ON CONFLICT (欄位)` 推不出部分索引，
   而這一支的 `on conflict` **帶了一模一樣的 where**，所以現在是對的。
   改的時候三個地方要一起改，漏一個就是「存不進去」。

### ② 契約會自動長出繳款單　→ ✅ **已有防護**（階段 0 查證）

`gen_contract_orders`（最新定義在 migration_93）**第一行就擋了**：

```sql
if ct.start_date is null or ct.end_date is null then return; end if;
```

不是靠 null 的三值邏輯僥倖 —— 是明確寫的。**不用改。**

`schema-baseline.sql:779` 那支舊版的月租單產生器也一樣有防護，
而且多一道 `if not ct.active` —— **這順帶證實了 4.5 節的第一個檢查項**：
停用的契約不會再長月租單。

### ③ 契約會自動長出營收認列　→ ✅ **已有防護**（階段 0 查證）

`gen_contract_recognitions`（migration_137 / 138）開頭：

```sql
if ct.start_date is null or ct.end_date is null
   or ct.monthly_rent is null or ct.monthly_rent <= 0 then return; end if;
```

日期與租金都擋了。**不用改。**

★ 但查出一件要注意的事:**表單填的是 `amount_per_period`，
  認列看的是 `monthly_rent`** —— 存檔時由前端換算
  （`contracts/page.tsx:340`：`monthly_rent = amount_per_period / 期數倍率`）。

  那一行寫的是 `(edit.amount_per_period || 0)`，所以訂金階段會存
  **`monthly_rent = 0`** 而不是 null。功能上安全（`<= 0` 一樣 return），
  但語意上「0 元租金」跟「還沒填」不一樣。
  → 實作時 `earnest_only` 要存 **null**，不是 0。

### ④ 放寬 NOT NULL 之後每一處都要處理 null　→ ✅ **前端本來就寬容**（階段 0 查證）

盤點結果，原本估計最貴的一項其實幾乎不用改：

| 位置 | 結果 |
|---|---|
| `contracts/page.tsx` 的型別 | ✅ 本來就是 `start_date: string \| null` |
| `statusOf`（第 213 行） | ✅ `c.end_date && …` —— null 時算「有效」 |
| 期間篩選（第 219 行） | ✅ `r.start_date \|\| ''` 之後 falsy 就跳過 |
| `strayPaid`（`contract-lifecycle.ts`） | ✅ 簽名就是 `start: string \| null`，內有 `if (start && …)` |
| Excel 匯出（第 77 行） | ✅ `c.amount_per_period \|\| (c.monthly_rent \|\| 0) * step` |
| `sync_customers` 的 `stay_from` | ✅ `min()` 忽略 null，`customers.stay_from` 本來就可空 |

**真正要動的只有兩處：**

- [ ] `contracts/page.tsx:329` 的註解說「end_date 是 NOT NULL」—— **會過時，要改**
- [ ] 存檔時 `earnest_only` 的 `monthly_rent` 要存 null 不是 0（見上）

### ⑤ `deposits.amount` 是觸發器同步過來的，不能直接改

migration_146 的教訓：

> 移轉時**不能**順手把 B 那列改小 —— 下次那張訂單一存檔就被蓋回去。

所以「訂金轉押金之後押金剩多少」**不能寫進 `deposits.amount`**，
要靠 `deposit_payments`（分筆收款，migration_147）記「已收多少」。

## 四、資料模型

### 4.1 `deposits` 加 `kind`

```sql
alter table deposits
  add column kind text not null default 'deposit'
    check (kind in ('deposit', 'earnest'));   -- 押金 / 訂金
```

**為什麼加欄位而不是開新表**：訂金與押金的生命週期一模一樣
（未收 → 已收 → 送審 → 排匯款 → 已退），退款流程、兩票審核、
`deposit_payments` 分筆收款、憑證上傳全部可以共用。
開新表等於把 `deposit-refund.ts`、`DepositRefundStep.tsx`、
請款審核頁那一整套複製一份 —— 而複製出來的那份會慢慢跟原本的不一樣。

### 4.2 `contracts` 加訂金欄位

```sql
alter table contracts
  add column earnest_amount numeric not null default 0,
  -- ★ 這一欄是「這張契約還在訂金階段」的旗標，不是金額
  add column earnest_only boolean not null default false;

alter table contracts alter column start_date drop not null;
alter table contracts alter column end_date drop not null;
alter table contracts alter column amount_per_period drop not null;
```

**為什麼要 `earnest_only` 而不是用「日期是不是 null」判斷**：
日期是 null 有很多種原因（舊資料、匯入失敗、有人手動清掉）。
用一個明確的旗標，畫面才講得出「這是訂金階段」而不是「這張契約壞了」。

### 4.3 轉押的痕跡

比照 migration_146 的移房，四個欄位：

```sql
alter table deposits
  add column converted_to_deposit_id uuid references deposits(id),
  add column converted_from_earnest_id uuid references deposits(id),
  add column converted_by uuid,
  add column converted_at timestamptz;
```

**為什麼備註寫中文字不夠**（migration_146 已經吃過這個虧）：
報表要把「轉押」排除在「本月收款／本月退款」之外。
分不出來的話，當月的暫收報表會憑空多一筆退款和一筆收款，
而總額又剛好對得起來（錢沒有離開公司）—— **不會有任何跡象**。

### 4.4 沒收訂金

```sql
alter table deposits
  add column forfeited_on date,
  add column forfeit_order_id uuid references orders(id),
  add column forfeited_by uuid;
```

**★ 完全不用新增會計科目，也不用改 `fee-types.ts`。**

使用者一開始說「違約金」，後來改成「其他」—— 而**「其他」正好對上
一條既有的業務決定**。`fee-types.ts` 的檔頭寫著：

> 【取消相關的收入歸在「其他」】
> Airbnb 取消收入、取消預訂這幾種（2026-08 時 73 筆、約 150 萬）
> 刻意不另立科目，明細留在備註裡。這是業務上的決定，不是漏掉。

沒收訂金就是「取消相關的收入」，歸在同一處是一致的。

代價那段也一起沿用：**營收報表的「其他」會包含這筆錢，光看報表分不出組成**，
要回訂單看項目名稱（「取消入住」）。之後若要分開，加一個科目再重新標記即可。

**產生的那筆一次性收入長這樣：**

| 欄位 | 值 |
|---|---|
| `source` | `oneoff` |
| `fee_type` | `其他` |
| `item_name` | `取消入住` |
| `amount` | 訂金金額 |
| `checkin` / `checkout` | 沒收日（一次性收入起訖同一天） |
| `deposit_id` | **指向那筆訂金** |
| `estate_id` / `property_id` / `guest_name` | 從契約帶 |

**★ `deposits.deposit_id` 這條路 migration_157 已經鋪好了** ——
押金加費就是掛在 `orders.deposit_id` 上。沒收訂金照同一套，
所以「這筆收入是從哪筆暫收來的」查得到，
而且 `order_fee_deposit_guard` 那些既有的保護一併適用。

**★ 冪等**：`forfeit_order_id` 記著產生的那張訂單，
按第二次不會再長一筆。沒有這個欄位的話，重複按就是重複收入 ——
而總額看起來只是「多了一筆」，沒有任何跡象說它是重複的。

### 4.5 沒收之後：契約停用，收入鎖住

使用者先說「契約刪了」，再改成「契約停掉」。**改對了** ——
下面是查證的結果，兩者差很多。

#### 如果真的刪契約，會發生這些事

`mark_deposits_orphaned()`（migration_56，`before delete on contracts`）：

```sql
delete from deposits where contract_id = old.id and received_on is null;
update deposits set orphaned = true,
       note = concat_ws('・', note, '來源契約已刪除 …')
 where contract_id = old.id;
```

已收的訂金**不會被刪**，會標成 `orphaned = true` 留著。
而 `deposits_contract_id_fkey` 是 **`ON DELETE SET NULL`**（已查證），
所以 `trash_collect_children` 不會把它當子列收走
（那支只收 `confdeltype = 'c'` 也就是 CASCADE 的）。
`orders.deposit_id` 也是 `on delete set null` —— 收入完全不受影響。

**所以「刪契約」技術上是安全的。** 但有一個語意問題：

> 訂金會變成**孤兒**，而「孤兒」的意思是「來源不見了，要人處理」。
> 沒收過的訂金**已經處理完了** —— 它變成收入了。
> 標成孤兒會讓它出現在暫收管理的「孤兒」那一格，
> 而看的人會以為那裡有事情要做。

#### 停用就沒有這個問題

`active = false` **不觸發任何東西**：不刪、不標孤兒、不 cascade。
訂金留在「已沒收」，收入留著，契約查得到但不出現在有效清單裡。

**契約停用的連帶效果要確認**（實作時的檢查項）：

- [ ] 停用的契約不會再長月租單（照理說會停，但要實測）
- [ ] 停用的契約不出現在契約列表的預設篩選
- [ ] 停用**不會**動到 deposits（`sync_contract_deposits` 只在
      `deposit / estate_id / room / tenant_name` 變動時觸發，`active` 不在裡面）

#### 收入不能刪 —— 沿用 migration_157 的鎖

使用者指定「沒收產生的收入不能刪」。**不需要新機制** ——
`order_locked_reason()`（migration_157）已經在做這件事，
現在只是多一個理由：

```sql
-- 現行：押金已退款 / 已掛加費 → 鎖住
-- 新增：deposit_id 指向一筆 forfeited_on 有值的訂金 → 鎖住
'這筆是沒收訂金產生的收入，不能刪除或修改。'
```

`trg_orders_lock_guard` 是 `before update or delete`，所以**改也擋、刪也擋**。
會計與總管理員仍可放行（那支既有的例外）—— 打錯一個字不該只能請人下 SQL。

★ 為什麼不能刪:那筆收入已經進當月營收了。刪掉的話當月數字會少一筆，
  而訂金那邊還記著 `forfeited_on` —— 兩邊對不起來，
  **而且沒有任何一張報表會報錯**。

## 五、狀態機

### 訂金

```
建立契約（勾訂金）
      ↓
   未付訂金          received_on is null
      ↓ 收款
   已收訂金          received_on 有值
      ↓
      ↓  ★ 第三階段，三選一（2026-08-24 使用者指定）
      ↓
      ├─ 退款 ──→ 送審 → 排匯款 → 已退訂金      兩票，走請款審核
      │            refund_status: pending → approved，returned_on 有值
      │            錢真的匯出去
      │
      ├─ 沒收 ──→ 已沒收                        不用兩票
      │            forfeited_on 有值 ＋ 產生一筆 oneoff 收入
      │            錢留下來，變成營收
      │
      └─ 轉押 ──→ 已退｜轉押                    不用兩票
                   converted_to_deposit_id 有值
                   錢沒有離開公司，換一個名目
```

### ★ 三條路互斥，而且**走過就不能再走**

|  | 客人的行為 | 錢去哪 | 兩票 |
|---|---|---|---|
| 退款 | 不租了，錢還他 | 匯出去 | **要** |
| 沒收 | 不租了，訂金不退 | 留下來變營收 | 不用 |
| 轉押 | 要租 | 沒有離開公司 | 不用 |

**資料庫要擋「走了一條再走另一條」。** 三種組合都會出事：

- 已退 → 再沒收：錢還給他了卻認列成收入，**營收憑空多一筆**
- 已沒收 → 再退款：收入認列過了又匯錢出去，**兩邊都錯**
- 已轉押 → 再退款：押金那邊已經算收到了，退了會變成押金憑空少一筆

三種都不會報錯，都只會讓某一張報表安靜地錯掉。
所以是**資料庫的 check，不是畫面的判斷**。

### ★ 為什麼沒收不用兩票

兩票在擋的是「錢被匯到不該去的帳戶」（migration_146 的理由）。
**沒收的錢不會離開公司** —— 它從負債變成收入，帳上位置換了，
但沒有任何一塊錢流出去。沒有收款帳號可填，硬套審核只會逼人亂填。

代價是要留人證：`forfeited_by` / `forfeited_on`，
而且沒收會**產生一筆看得見的營收**——那本身就是最好的稽核痕跡。

### 押金（現行，不動）

```
未收款 → 已收款(暫收中) → 送審 → 排匯款 → 已退款
```

### ★ 為什麼轉押不用兩票

跟移房同一個理由（migration_146 的檔頭）：

> 兩票在擋的是「錢被匯到不該去的帳戶」。移轉的錢**沒有離開公司**，
> 沒有收款帳號可填。硬套流程只會逼人亂填一個帳號進去，
> 而那個假帳號將來看起來跟真的一模一樣。

代價是要留人證：`converted_by` / `converted_at`。

## 六、流程

```
① 客人說要租 → 建契約，勾「訂金」，填 物業 / 房源 / 姓名 / 訂金金額
                   ↓
              暫收管理出現一列「未付訂金」

② 收到訂金 → 按「收款」，填日期、方式、帳號
                   ↓
              「已收訂金」

③ 知道契約內容 → 回契約補 租期起訖、每月租金、押金金額
                   ↓
              暫收管理長出第二列「未收押金」

④ 按「轉押」→ 訂金那一列變「已退｜轉押」
              押金那一列多一筆 deposit_payments（金額 = 訂金）
                   ↓
              訂金 = 押金 → 押金變「已收押金」
              訂金 < 押金 → 押金顯示「已收 10,000 / 尚欠 20,000」

⑤ 收押金餘款 → 押金變「已收押金」

⑥ 取消勾選「訂金」→ 契約變正式契約 → 開始長月租單
```

**⚠ 第 ⑥ 步是這個流程最脆弱的地方。**

三個欄位既然是**選填**（可以隨時填），「填了」就不能當成「生效了」——
所以轉正必須是人明確按下去的動作（取消勾選）。

**★ 三個欄位沒填完就不能取消勾選**（2026-08-24 使用者指定）。

  取消勾選 = 這張契約要開始長月租單了。租期或租金是空的話，
  長出來的單會是「日期 null、金額 null」——
  而那種單**不會報錯**，只會在營收報表上變成一個看不懂的空格。

  擋的時候要**說出缺哪一個**:

      還不能取消「只收訂金」—— 還沒填：租期迄、每月租金

  只說「請填完必填欄位」的話，使用者得自己一格一格找。
  這一頁有十幾個欄位。

★ 第 ④ 步是**三條路之一**，不是必經的一步:

    要租         → ④ 轉押
    不租、退他   → 退訂金（兩票，走請款審核）
    不租、不退   → 沒收（產生一筆「取消入住」的一次性收入）

  三條互斥，走過一條就不能再走另一條 —— 資料庫要擋，見第五節。

## 七、畫面

### 7.1 契約表單

押金欄位下方加一列：

```
押金(台幣)  [        0 ]
☐ 只收訂金（契約內容還沒確定）
   勾了之後只要填 物業、房源、姓名。租期與租金之後再補。
   訂金 [        0 ]
```

勾選時（2026-08-24 使用者補充：「三個欄位放寬成**選填**」）：

- 租期起、租期迄、每月租金 → **仍然可以填，只是不強制**
- 必填紅星拿掉，改成灰色的「選填」
- 底部加一行說明：「這張契約還不會產生月租單。填好租期與租金、取消勾選之後才會。」

★ **不是變灰、不是隱藏、不是 disabled。**

  我第一版寫成 `disabled`，那是錯的。收訂金的當下可能已經知道租期了
  （「大概九月一號起租」），只是還沒定案 —— 擋著他填，
  他就得記在別的地方，然後補的時候重打一次。

  「不強制」與「不能填」是兩件事。這裡要的是前者。

★ 那三個欄位有填的時候仍然**不會**產生月租單 —— 產不產生只看
  `earnest_only` 這個旗標。這是刻意的：填了資料跟「這張契約生效了」
  是兩回事，中間那一步（取消勾選）必須是人明確按下去的。

### 7.2 暫收管理（原押金管理）

選單名稱：**押金管理 → 暫收管理**

#### 統計卡片改成兩列（2026-08-24 使用者指定：「卡片有兩列」）

現行是一列四張（未收款 / 已收款 / 已退款 / 孤兒）。改成：

```
訂金   未付訂金 3      已收訂金 5      已退 2      已沒收 1      轉押 4
押金   未收款  12      已收款  38      已退款 20   孤兒 1
```

**★ 兩列不是「同一組數字分兩行」，是兩組不同的數字。**

訂金有「已沒收」與「轉押」，押金沒有；押金有「孤兒」，訂金沒有
（訂金不會變孤兒 —— 契約刪掉時訂金跟著刪）。
硬做成同一組欄位的話，會有一半的格子永遠是 0，
而**永遠是 0 的格子會讓人以為那個功能壞了**。

點卡片 = 同時切換「訂金/押金」與「狀態」兩個條件。

#### 列表的頁籤

```
全部 │ 訂金 │ 押金
```

**為什麼是頁籤不是篩選下拉**：訂金與押金是兩件不同的錢，
會計對帳時是分開對的。下拉選單會讓人以為「預設看到的是全部」，
而實際上他多半只想看其中一種。

#### 訂金的檢視抽屜

底部三顆按鈕（使用者：「訂金第三階段改成 沒收／退款／轉押金」）：

```
[ 沒收 ]  [ 退款 ]  [ 轉押金 ]        ← 已收訂金時
```

- 三顆**都留著但會變灰**，走過一條之後其餘兩顆灰掉並寫出原因
  （「已經沒收了，不能再退款」）——
  藏起來的話使用者會問「退款鈕去哪了」（2026-08-22 的原則）
- **沒收要跳確認**，而且要講出後果：
  「訂金 10,000 會變成一筆『取消入住』的一次性收入，計入本月營收。
  　這個動作不能復原。」

  ★ 沒收是這三條路裡唯一**產生營收**的 —— 按錯的後果是當月數字多一筆，
    而報表看起來完全正常。所以確認視窗要說出金額與科目。
