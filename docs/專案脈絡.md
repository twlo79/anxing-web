## ⚠️ 部署鐵則

**1. 推之前一定要在本機驗證**

```powershell
npx tsc --noEmit
npm run build
```

`next dev` 不跑完整型別檢查，本機看起來正常的程式碼可能 build 不過。

**2. SQL 一定先跑，前端才推**

migration 結尾必須帶 `notify pgrst, 'reload schema';`。不重載 PostgREST 的 schema cache，新欄位在 API 層仍視為不存在，查詢會回 400、整頁掛掉。

**3. 驗證檔案有沒有真的換到，看 bundle size**

`npm run build` 輸出裡對應路由的大小沒變化就是編到舊檔。

**4. 檔案大小用位元組，不要用行數**

PowerShell 的 `(Get-Content x).Count` 會受編碼與換行符影響。用 `(Get-Item "路徑").Length`。

**5. `git add -A` 之前先看 `git status --short`**

Windows 端 `core.autocrlf` 的關係，某些操作會讓整個 repo 顯示為 modified。冒出一大串不相干檔案就先停手，別推出一個動到全 repo 的巨大 diff。

## 資料結構要點

### 收入鏈

**`orders` 是交易中心。** 長租月租單的 key 格式為 `LT_{room}_{YYYYMM}`，**逐月一列**，不論契約 cadence 是月繳或年繳。加費為 `CFEE_`、`FEE_`，移房子單為 `MOVE_`。Airbnb 訂單的 `order_key` **就是確認碼本身**（如 `HMZJNPMPMN`），沒有前綴。

**`gen_contract_orders` 觸發器** —— 編輯契約時會依租期逐月 upsert 月租單。**只覆寫 `imported_via='contract'` 且 `paid=false` 的列**。

**`revenue_recognitions`** 由觸發器維護，一張訂單會按月份比例攤分成多列。**勿手改**。

**`contract_payments`** 存在但前端未使用；收款狀態記在 `orders.paid` / `paid_at`。

### 支出鏈（2026-07-30 新增）

```
purchase_requests ──► purchase_request_items ──► expenses
                            (填採購日時逐項產生，1 對 1)
```

- `purchase_requests`：狀態 `draft` → `pending` → `approved` / `rejected`
- **兩票並行無先後**：`manager` 一票、`super_admin` 一票，兩票到齊才 `approved`
- **總額 < 3000 兩票全免**，送出即核可。門檻看整張單總額（防拆單規避）
- `account_codes`：15 個預設會計科目
- 收入與支出**目前不在系統內相減**，看損益要兩邊各自匯出 Excel 合併

## 2026-07-30～31 完成的工作

### A. Airbnb 每日自動同步

建了兩支 Cowork 排程（每天 07:07 評價、07:26 訂單），架構是：**在 airbnb.com 分頁跑 JS**（同源帶 cookie 抓資料）→ **跨域 POST 回 ERP 的 `/api/import/*`**（`x-import-key` 認證）。service_role key 全程留在 Vultr。

已驗證的 Airbnb API：

| 用途 | 端點 | 關鍵限制 |
|---|---|---|
| 評價 | `ReviewsSectionQuery`（persisted query hash `015be4ee…d5e14`） | `limit` 上限 **50**，給更大回 null |
| 訂單 | `/api/v2/reservations` | 每頁上限 **40**；`sort_field` 只支援 `start_date`，`booked_date` 回 422 |
| 搭檔收款 | `StayHostingDetailsQuery`（hash `c6555d61…ea824`） | 用 `sectionId === "PAYMENTINFO_SECTION"` 搜尋，**不要用固定索引** |

**訂單改成完整覆蓋而非滑動視窗**：未來/進行中全掃（`date_min=TODAY`，約 60 筆）+ 取消單全掃（約 330 筆）+ 最近已結束 100 筆。約 14 次請求。因為 `booked_date` 不能排序，滑動視窗抓不準新單。

**撤評偵測（哨兵機制）**：每天 50 筆的視窗永遠發現不了八個月前那筆被撤掉。作法是先做增量寫入，再比 `DB 筆數` vs `Airbnb totalCount`，並用「上次最新評價 id 在今天清單裡的位置」算出真正新增數——這樣「今天新增 1 則、同時撤 1 則」的淨零情況也抓得到。只有落差出現時才跑全量對帳（30 次請求）。

**新增 `/api/import/reconcile`**，三道護欄：抓取完整性（`totalCount` 須相符）、比例閘（不足現有 90% 中止）、刪除上限（`maxDelete` 預設 5）。`dryRun` **預設 true**。實測抓到一筆真的撤評（Fabien，台視台3），已刪除。

**修掉 `airbnb-orders` 的兩個 bug**：
1. 取消且無收入原本直接 `continue` 跳過 → 已匯入的舊金額會一直留著被算進營收。現在會把該列改成 `airbnb_cancelled`、`amount=0`，但**只動 `paid=false` 的列**，已收款的列進 `needsAttention` 交人工判斷
2. 取消單原本只看 `earnings` 不看 `cohost`，整筆走搭檔收款的取消費會被丟掉

### B. ⚠️ locale 事故（重要，別再犯）

排程 prompt 一開始寫了 `locale=en`，造成 **50 筆評價的 `property_id` 被寫成 null**。

原因：英文 locale 下 Airbnb 會把 listing 名翻成英文（`Modern Minimalist German Design/...`），與 DB 和訂單 API 裡的中文原名對不上 → `/api/import/reviews` 解析不到房源 → upsert 把原本正確的值蓋成 null。

**所有 Airbnb API 一律用 `locale=zh-TW`。** 舊的匯入程式本來就是跑中文介面（端點裡的 `parseStayZh` 專門解析「2026年5月25日至7月21日」，就是證據）。

已修復（45 筆靠 listing_id、5 筆靠訂單日期比對），並加了三層防護：
1. 兩支排程 prompt 改 `zh-TW`，並寫明事故原因防止被改回去
2. `/api/import/reviews` 房源解析改三層：`listing_id` → 名稱備援（從既有評價自學）→ **保留既有值**。最後一層是關鍵，解析不出來時絕不寫 null
3. 三層都失敗的列進回傳的 `unresolved`，不再靜默留空

### C. 請款與支出模組

新頁面 `/purchases`、`/expenses`（原本是空殼）。設計文件 `docs/expenses.md`，同仁操作手冊 `docs/會計手冊.md`。

**規則寫在資料庫，不是前端：**

| 規則 | 實作位置 | 為什麼 |
|---|---|---|
| 未核可不能採購 | CHECK 約束 `pr_purchase_chk` | 前端藏按鈕只是體驗，繞過前端還是插不進去 |
| 免核門檻 3000、兩票才算數 | `pr_apply_status()` 觸發器 | 讓前端算等於改前端就能繞過門檻 |
| `total_amount` | `sync_pr_total()` 觸發器 | 前端送總額 = 把規則交給呼叫端 |
| **會計不得核可** | `pr_guard_votes()` 觸發器 | **RLS 管不到欄位層級** —— 會計為了填採購日必須能 update 該列 |
| 不得核可自己送的單 | 同上 + RLS | 主管也會送單，不擋的話那一票形同虛設 |
| 連動支出不可刪（除 super_admin） | RLS `exp_delete` | 兩票核可是為了管錢，紀錄一個人就能刪等於白設；且刪除是靜默的，重填採購日也救不回來 |

**`accountant` 是後加的角色**，既有表 policy 都明列角色名，新角色預設什麼都讀不到。開放方式是**追加 `for select` policy**，不改寫既有的——permissive policy 是 OR 關係，追加不會動到原本判斷。

### D. 短租 Excel 匯出

`/shortterm` 加了下載按鈕。**關鍵差異**：這頁是伺服器端分頁，`rows` 只有當前 50 筆，直接匯出會只得到 50 筆。所以匯出時重新向伺服器要完整結果，篩選與排序條件跟 `load()` 逐項對齊。

## 協作注意事項

**改動前要先看到實際程式碼。** 頁面檔案都是單檔 400–850 行、狀態與渲染交織，靠猜變數名寫出來的程式碼只會增加對接成本。

**讀 repo**：`web_fetch` 對 GitHub 有網域限制。最可靠的方式是掛載本機資料夾直接讀。

**三頁的排序機制刻意不同**：契約與營收是前端排序（`sortRows`），短租是伺服器端排序（`.order()`），因為它是伺服器端分頁，前端排只會排到當前頁。空值一律殿後；房號要自然排序（`3A5` 要在 `13B1` 前面）。
