# 採購需求（規格）

> 狀態：**資料庫與提需求端完成；會計端未做**（2026-08-17）
> 取代現行的 Google 表單「採購需求單」。

---

## 為什麼要做

現在是 Google 表單。填完之後那份資料躺在試算表裡，而請款在 ERP ——
會計要自己在兩個系統之間搬，搬的過程沒有痕跡：

- 哪些需求還沒處理？看不出來
- 這張請款單是為了哪個需求開的？只有經手人知道
- 同一張需求分兩次買，第二次買了什麼？要翻對話紀錄

**把需求單放進 ERP，是為了讓「需求 → 請款」這條線自己留下紀錄。**

---

## 一、兩個入口，同一份資料

| 入口 | 給誰 | 做什麼 |
|---|---|---|
| **房務管理 → 採購需求** | 提需求的人（房務、管家） | 填單、看自己提的、看進度 |
| **請款單控管 → 採購需求區塊** | 會計 | 看全部待處理、詢價、勾選拆單、轉請款 |

**不是兩份資料，是兩個視角。** 同一張需求單在兩邊都看得到，狀態即時同步。

會計那一側是**待辦清單**：進請款頁第一眼就知道「有幾件事等我處理」，
不用去別的頁面找。

## 二、流程

```
① 提需求          房務管理 → 採購需求 → 新增
   品名、規格、數量、用途（物業）、備註
   **沒有金額** —— 提的人不知道要多少錢
        │
        ▼
② 會計看到        請款單控管 → 採購需求區塊（待處理 N 件）
        │
        ▼
③ 詢價            會計去問價，把單價記回項目上（選填）
        │
        ▼
④ 勾選拆單        勾要買的項目 → 「轉請款單」
   一張需求可以拆成多張請款單，剩下的項目留在需求單上
        │
        ▼
⑤ 填金額送審      請款單帶入品名／數量／物業，會計填實際金額
        │
        ▼
⑥ 兩票核可 → 自動產生支出（既有流程，不動）
```

### 幾個刻意的決定

**需求單不審核。** 它只是「我需要這個」的登記，任何人都可以提。
真正把關的是請款單的兩票核可 —— 錢在那裡才出去。

多一道需求審核會讓提需求變麻煩，而提需求變麻煩的結果是**大家繼續用 LINE 講**，
那就回到起點了。

**金額在轉請款時才填。** 提需求的人不知道價錢，逼他填只會得到亂數。
詢價後的單價可以先記在項目上當參考，但那是選填，也不是最終值。

**用途選「物業」不選房源。** 原本的 Google 表單選房源 ——
但採購幾乎都是整棟共用的（清潔用品、備品、工具），
選到房號反而要每次想「那算哪一間的」。

## 三、資料結構

```
purchase_demands  需求單
├ id, demand_no（DM-YYYYMM-NNN）
├ requester_id    誰提的
├ requested_on    哪天提的
├ note            整張單的備註
└ status          open / partial / done / cancelled  ← 由項目推導，不手動改
                  顯示成：尚未採購 / 部分採購 / 採購中 / 已作廢

purchase_demand_items  需求項目
├ id, demand_id
├ item_name       品名           必填
├ spec            規格說明
├ qty             數量           必填
├ estate_id       用途（物業）    必填
├ unit_price_est  詢價單價        選填，參考用
├ note            備註
├ status          pending / quoted / requested / done / cancelled
└ request_item_id → purchase_request_items.id   被哪張請款單領走
```

### 狀態怎麼顯示（2026-08-17 使用者指定）

| 欄位值 | 畫面上寫 | 意思 |
|---|---|---|
| `open` | **尚未採購** | 一項都還沒進請款 |
| `partial` | **部分採購** | 有些進請款了、有些還沒 |
| `done` | **採購中** | 全部都進請款了 |
| `cancelled` | 已作廢 | |

> **「採購中」不是「完成」。** 進請款只代表會計開始處理，
> 東西還沒到、錢也還沒付。
>
> 欄位值叫 `done`，直覺會翻成「已完成」—— 然後畫面上就會出現
> 「已完成」卻沒有人拿到東西。標籤集中在 `lib/purchase-demand.ts`，
> 不要在畫面上各寫一份。
>
> 真正的完成（收到貨）**還沒有狀態**。要的話加第四個，
> 不要把「採購中」偷偷改成完成。

**部分採購要講得出還缺什麼。** 只給一個標籤的話，提需求的人還是得
點開單子一項一項看 —— 而答案就是幾個品名而已：

```
已進請款 2 / 5・還缺：垃圾袋、抹布、手套
```

最多列三樣，再多就 `等 N 樣` —— 列表的一列只有一行的高度。

### 為什麼狀態掛在「項目」不掛在「單」

一張需求單可以分幾次買。狀態放在單上的話，
「買了三項還剩兩項」只能表達成一個含糊的 `partial` ——
而那五項各自到哪了，看不出來。

單的 `status` 由項目推導：全部 `pending` → `open`；
有些已請款 → `partial`；全部 `requested`/`done` → `done`。
**推導出來的，不要讓人手動改** —— 手動改就會跟項目對不上。

### 為什麼是 `request_item_id` 不是 `request_id`

勾選是以**項目**為單位的。一張請款單可能只領走五項裡的兩項，
而那兩項各自對到請款單裡的一列。

指到單的話，「這一項在請款單上是哪一列」就查不到 ——
而對帳時要的正是那個。

## 四、畫面

### 房務管理 → 採購需求

```
[+ 新增採購需求]                              共 12 件・待處理 5

┌──────────────────────────────────────────┐
│ DM-202608-003   唐   08-15        ⏳ 待處理 3 / 已請款 2 │
│ ├ 洗衣精 ×6        時兆      已請款 PR-202608-011      │
│ ├ 拖把 ×4          開封      已請款 PR-202608-011      │
│ ├ 垃圾袋 ×20       正隆      待處理                    │
│ ├ 抹布 ×30         正隆      待處理                    │
│ └ 手套 ×10         時兆      待處理                    │
└──────────────────────────────────────────┘
```

**每一項自己顯示狀態與被哪張請款單領走** ——
提需求的人問「我上次要的拖把買了沒」，自己看得到答案。

### 請款單控管 → 採購需求區塊

放在頁面上方（請款單列表之前），**只有待處理的**：

```
📋 採購需求  待處理 5 項                              [全部展開]
┌──────────────────────────────────────────┐
│ ☐ 垃圾袋 ×20    正隆   唐 08-15   詢價 [____]        │
│ ☐ 抹布 ×30      正隆   唐 08-15   詢價 [____]        │
│ ☐ 手套 ×10      時兆   唐 08-15   詢價 [____]        │
│ ☐ 燈泡 ×8       開封   月 08-16   詢價 [____]        │
│                                                        │
│ 已勾選 0 項                        [轉成請款單]        │
└──────────────────────────────────────────┘
```

**跨需求單勾選** —— 會計是「這次去五金行要買什麼」的思維，
不是「這張單要處理什麼」。三張需求單裡的東西可能一趟就買齊。

沒有待處理項目時整塊不顯示 —— 空狀態佔的高度是請款單列表要用的。

### 轉請款單

勾選後開請款單表單，**帶入**：品名、數量、用途物業、規格（進備註）。
會計填金額、廠商、付款方式，其餘走既有的請款流程。

存檔成功後把那幾項的 `status` 改成 `requested`、寫入 `request_item_id`。

## 五、權限

| 角色 | 提需求 | 看全部 | 詢價 | 轉請款 |
|---|:---:|:---:|:---:|:---:|
| 房務 cleaner | ✓ | 只看自己的 | — | — |
| 管家 housekeeper | ✓ | 只看自己的 | — | — |
| 會計 accountant | ✓ | ✓ | ✓ | ✓ |
| 主管 manager | ✓ | ✓ | ✓ | ✓ |
| 總經理 super_admin | ✓ | ✓ | ✓ | ✓ |

> ⚠ **`cleaner` 與 `housekeeper` 的 RLS 相同**（`migration_131`）。
> 「只看自己的」要靠 `requester_id = auth.uid()` 寫進 policy，
> 不能只靠前端篩 —— 那擋不住打網址。

RLS 三條：

```sql
-- 自己提的看得到、改得動（還沒轉請款前）
demand_own    for all   using (requester_id = auth.uid())
-- 會計以上看得到全部
demand_read   for select using (current_role_of() in ('accountant','manager','super_admin'))
-- 會計以上改得動（詢價、取消）
demand_write  for all    using (current_role_of() in ('accountant','manager','super_admin'))
```

**已經轉請款的項目不能改** —— 由觸發器擋，不是靠前端。
改了金額對不上請款單，而那不會報錯。

---

## 六、要注意的地方

**① 需求單刪除 vs 已請款**
已經轉成請款單的項目不能刪。整張單要作廢的話，只能作廢還沒請款的項目。

**② 請款單被駁回**
那幾項要回到 `pending`，重新出現在會計的待辦裡 ——
不然它們會靜靜地卡在 `requested` 永遠不再出現。
**這是最容易漏的一條**，要寫在觸發器裡。

**③ 通知**
需求單提交 → 通知會計。這要走既有的四種通知之一（`orders`/`approvals`/`reviews`/`cleaning`），
或加第五種 —— 加第五種要動 `migration_92` 的 `notification_prefs` 與設定頁。

**④ 數量與單位**
Google 表單沒有單位欄。「6」是六瓶還是六箱？
建議 `qty` 旁邊加一個 `unit`（瓶／箱／個／組），選填但預設「個」。

## 七、已確認（2026-08-17）

| 問題 | 決定 |
|---|---|
| 單號格式 | `DM-YYYYMM-NNN`，流水號**按月重來**。全域流水三年後會變成 `DM-202608-1247`，那個數字沒有人記得住 |
| 通知 | **加第五種：採購需求**（`notification_prefs.purchasing`）。不塞進「審核」—— 關掉審核通知的人會連請款核可也收不到 |
| 單位欄 | 不加 |
| 房務可否提需求 | **可以**，而且看得到自己那幾項的狀態連動（已採購） |
| 請款駁回 | **那幾項全部退回待辦**（`status` 回 `pending`、`request_item_id` 清空） |
