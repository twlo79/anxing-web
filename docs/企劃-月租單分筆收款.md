# 企劃：月租單分筆收款

> 2026-08-25　使用者提出　**這份是企劃，還沒有寫任何程式碼**

---

## 一、需求原文

> 這邊收費可以多筆收。
>
> 1. 確認收費下方加入一個「多筆收入」
> 2. 勾選後開放可填多筆
> 3. 每筆鍵入包含 日期、金額、收入方式：現金／匯款
> 4. 確認收入也是鍵入 日期、金額、收入方式
>
> 收款流程：
> 1. 鍵入一次性費用
> 2. 確認收款 → 鍵入 日期、金額、收入方式
> 3. 多筆收款 → 鍵入 日期、金額、收入方式，可看明細，
>    直到收入達到訂單金額 → 確認收款填入最後日期與訂單金額
> 4. 也確認一次性費用 → 直接填到收入

**追加（2026-08-25 問答）：**

| # | 問題 | 決定 |
|---|---|---|
| 1 | 收到多少算滿 | **整期應收合計**（房租＋管理費＋一次性－折讓） |
| 2 | 收滿之後 | **自動標記整期已收** |
| 3 | 收款方式 | **只留現金與匯款** |
| 4 | 匯款 | 要有**內扣**選項；有內扣會減少收入 → 變成郵電費支出 |

## 二、★★ 最重要的發現：八成已經做好了

這個需求踩到的每一塊，系統裡**都已經存在**，只是沒有接到契約頁：

| 需求 | 現況 |
|---|---|
| 分筆收款的資料表 | ✅ `order_payments`（migration_147） |
| 分筆收款的畫面 | ✅ `src/components/OrderPayments.tsx`（日期、金額、方式、帳號、備註、憑證照片） |
| 已收合計 | ✅ `orders.paid_amount`，由觸發器維護，**前端不自己算** |
| 匯款內扣 → 郵電費支出 | ✅ migration_164（`order_payments.fee_amount` / `fee_on`，冪等） |
| 一次性費用跟著整期收 | ✅ 已經是現行行為 |

**月租單本身就是 `orders`**（`LT_{房號}_{YYYYMM}`），跟短租訂單同一張表。
所以 `OrderPayments` 理論上直接掛得上去。

★ 這代表**不需要新表、大概率不需要 migration**。
需求 3 與 4 已經完全滿足，需求 1、2 是接線。

## 三、⚠ 唯一真正的難題：一期有好幾張單

`OrderPayments` 綁的是**一張 order**：

```ts
const due  = Math.round(Number(order.amount) || 0);   // 那一張的金額
const rest = remaining({ amount: order.amount, paid_amount: paidAmount });
```

而畫面上那一期是**多張單加起來**（`periodTotal()`）：

```
房租    $146,018   ← 一張（季繳就是三張）月租單
管理費    $8,982   ← 另一張，imported_via = 'contract_fee'
────────────────
應收     $155,000   ← t.net
```

**收 $155,000 這件事沒有一張單裝得下。**

### 三個做法

| | 做法 | 問題 |
|---|---|---|
| A | 每張單各自分筆收 | 一期要開三次收款視窗。使用者要的是「這一期收了多少」，不是「房租收了多少」 |
| B | **全部掛在房租那一張，目標金額用整期合計** | 那張單的 `paid_amount`（155,000）會大於它自己的 `amount`（146,018） |
| C | 新開一張「期別」表 | 最乾淨，但要動資料模型、觸發器、報表 —— 為了一個入口不值得 |

**建議 B。** 理由與代價：

- ★ **超收本來就不擋**（`deposit-payment.ts` 的既有規則：「超收不擋，只問一聲」），
  資料庫沒有 `paid_amount <= amount` 的約束 —— 查證過了，B 存得進去。
- 只要把 `due` 換成整期合計，畫面上的「尚欠」就是對的，也不會誤報超收。

★★ **代價要講清楚**：那張房租單的 `paid_amount` 從此不等於「房租收了多少」，
而是「這一期收了多少」。**任何直接讀 `orders.paid_amount` 的地方都會看到這個數字。**
目前只有短租頁與這個元件在讀它，但這是一筆需要記在 README 的債。

## 四、要做什麼

### 4.1 `OrderPayments` 加三個選填 prop

```ts
dueOverride?: number;      // 目標金額。不給就用 order.amount（短租頁維持原狀）
methodOpts?: string[];     // 收款方式。不給就用現有四種
onSettled?: (lastPaidOn: string) => void;   // 收滿時通知母頁
```

★ **三個都是選填**。短租頁一行都不用改 —— 改動只加不減，
既有行為原封不動，這是能安心接上去的前提。

### 4.2 契約頁：期別卡加一個入口

「確認收款」旁邊加「**分筆收款**」。點開就是 `OrderPayments`，
`dueOverride = t.net`、`methodOpts = ['cash','transfer']`。

★ 使用者原文說的是「勾選後開放可填多筆」。改成**一顆按鈕**而不是勾選框：
勾選框要記狀態（記在哪？每一期一個？），而按鈕沒有這個問題。
不想分筆的人不按它，跟勾選框沒勾是一樣的效果。

### 4.3 收滿 → 自動標記整期已收（使用者指定）

```
onSettled(lastPaidOn) → setPeriodPaid(chunk, true, label)
                        收款日 = 最後一筆的 paid_on
```

★★ **這是使用者指定的，但它違背專案原則「建議，不自動」。**

風險是：金額打錯一個 0（1,550,000）也會「收滿」，然後整期自動變綠，
而**沒有人確認過**。所以實作時要做兩件事：

1. 自動標記之後跳一個明確的提示：「已收滿 $155,000，整期標記為已收（收款日 9/24）」
   —— 不是無聲完成
2. 超收時**不自動** —— 超收表示金額可能填錯了，那時候要人看一眼

### 4.4 收款方式只留現金與匯款

`methodOpts = ['cash', 'transfer']`。

★ 短租與押金維持四種 —— 那兩邊真的收過信用卡。
只有長租收斂，因為長租實務上只有這兩種。

---

## 五、不用做的

- **一次性費用** —— 已經跟著整期一起收（`setPeriodPaid` 的既有行為）
- **內扣／郵電費** —— migration_164 已經完成，`OrderPayments` 已經有那個勾選
- **憑證照片** —— `OrderPayments` 已經有

---

## 六、驗收

1. 一期應收 $155,000，分三筆收 5 萬、5 萬、5.5 萬 → 尚欠歸零、整期自動變綠
2. 第三筆改成 6 萬（超收）→ **不自動標記**，要問一聲
3. 匯款那筆勾內扣 30 → 支出多一筆郵電費 $30；把那筆收款刪掉 → 郵電費跟著消失
4. **短租頁的收款視窗行為完全沒變**（沒傳新 prop）
