# 帳戶管理（規格）

> 狀態：**演算法已實測，程式未寫**（2026-08-18）
> 三個銀行帳戶的流水鏡像。會計上傳對帳單 PDF，系統解析、去重、更新餘額。

---

## 為什麼要做

現在三個帳戶的餘額散在網銀裡。要知道「公司現在有多少現金」得逐一登入查。
而對帳時要翻 PDF 逐筆比對，那份 PDF 看完就關掉，下次再翻一次。

**把流水存進 ERP，是為了讓「現在有多少錢」變成一個看得到的數字。**

## 二、版面

```
┌─ 帳戶管理 ──────────────────────────────────────────┐
│  ┌────────────┐ ┌────────────┐ ┌────────────┐     │
│  │ 元大 70564 │ │ 元大 24145 │ │ 元大 48088 │     │
│  │   $81,977  │ │    $6,590  │ │  $262,433  │     │
│  │  至 06/30  │ │  至 06/30  │ │  至 06/30  │     │ ← 餘額 ＋ 對帳單截止日
│  └────────────┘ └────────────┘ └────────────┘     │
│                                    [⬆ 上傳對帳單]   │
├────────────────────────────────────────────────────┤
│  70564 │ 24145 │ 48088                              │
│  日期    摘要        對方       支出    存入    餘額  │
│  06/24  ＡＴＭ轉    國泰世華          80,000  81,977 │
│  06/23  企網付款    網內互轉  45,000          1,977 │
└────────────────────────────────────────────────────┘
```

**卡片要寫「至 MM/DD」** —— 只給一個數字的話，看的人不知道那是今天的還是三個月前的。
而餘額是「最後一次上傳的對帳單的期末」，不是即時的。

**最上面要有一個合計**（使用者確認 2026-08-18）：三個戶加起來 **351,000**（2025/06/30）。

合計有個陷阱：三份對帳單的截止日可能不一樣。
只上傳了兩份就顯示合計的話，那個數字是「兩個新的 ＋ 一個舊的」——
看起來像現在的現金，其實不是。

**所以合計旁邊要標最舊那一份的日期**，例如
「總計 $351,000（其中 24145 只到 03/31）」。
三份都對齊時就只寫一個日期。

## 三、上傳流程：丟檔案進去就好

> 使用者指定（2026-08-18）：
> 「不用選帳號，直接讀 PDF，裡面也有帳號。」

```
① 丟檔案（可一次多份）
      │
      ▼
② 從 PDF 認帳號
      │   帳號元大中崙-綜合活期-20992000170564
      │        │
      │        ├─ 認不出來    → 停：這份 PDF 找不到帳號
      │        └─ 系統沒登記  → 停：帳號 209920001705**64** 尚未建立，請先去建帳戶
      │
      ▼
③ 驗格式（**不寫入任何資料**）
      │  ├ 表頭還在不在、座標有沒有跑掉？
      │  ├ 逐筆餘額連不連得起來？
      │  └ 總計對不對得上？
      │
      ▼
④ 預覽：元大中崙 · 2025/01–06 · 新增 12 筆 / 重複 35 筆
      │
      ▼
⑤ 按「確認匯入」才寫進資料庫
```

### 為什麼不讓人選

PDF 裡就有帳號：

```
帳號元大中崙-綜合活期-20992000170564
```

**已經知道答案的事情不要問。** 讓人選再驗，是多開一個出錯的地方 ——
選錯了系統會擋（所以不危險），但那個擋是白費的一次來回。
直接讀，連選錯的機會都不存在。

順帶多一件事變得可行：**一次拖三份 PDF 進來**，各自認各自的帳戶。
要人選的話這件事做不到，因為三份要選三次。

### 認不出來的時候要停，不要猜

| 情況 | 做什麼 |
|---|---|
| PDF 裡抓不到帳號 | 停。「這份 PDF 找不到帳號 —— 是對帳單嗎？」 |
| 抓到了但系統沒這個帳戶 | 停。**把抓到的帳號印出來**，請人先去建帳戶 |
| 抓到兩個不同帳號 | 停。多半是兩份 PDF 被合併成一份了 |

第二項特別重要：**把帳號印出來**。
只說「查無此帳戶」的話，人不知道是自己傳錯檔還是帳戶沒建 ——
而把數字放上去，兩秒就分得出來。

### 比對規則

比對前把非數字都去掉（`2099-2000-170564` 與 `20992000170564` 是同一個）。

三個完整帳號都拿到了，所以**一律比完整帳號**。
`account_no_tail` 是退路 —— 將來多開一個帳戶而還沒拿到 PDF 時才用得上。

**不論比完整帳號還是末五碼，都只准比「解析出來的帳號欄位」，
不可以在整份 PDF 的文字裡搜。**
元大這份的票據號碼長這樣：

```
012-0000341168247682
```

那串數字裡隨時會出現 `24145` 或 `48088` —— 全文搜會撞上票據號碼，
然後整份流水記到錯的帳戶，靜靜地。

### 格式檢查具體檢查什麼

| 檢查 | 不過的意思 | 擋不擋 |
|---|---|---|
| 抽得到文字 | 這是掃描的 PDF，不是網銀下載的 | **擋** |
| 認得出帳號、且系統有登記 | 見上表 | **擋** |
| 第 1 頁找得到「支出金額 / 存入金額 / 帳面餘額」表頭 | 銀行改版，欄位換名字了 | **擋** |
| 三個表頭由左而右的順序正確 | 欄位順序變了 | **擋** |
| 解析出的筆數 > 0 | 期間內沒有交易，或解析失敗 | **擋** |
| PDF 上的序號 1…N 連續 | **有列被漏掉了** | **擋** |
| 逐筆「前一筆餘額 ± 金額 = 這筆餘額」 | 有筆漏了，或支出／存入判反了 | **擋** |
| `sum(支出)` `sum(存入)` 等於 footer 的「總計」 | 有筆漏了 | **擋** |

### ⚠️ 不可以檢查 x 座標落在固定範圍

原本規格寫「三個金額欄的 x 座標在預期範圍（±15pt）就放行，否則擋下」。
**實測發現這條規則會把 24145 整份擋掉。**

| | 70564 | 48088 | **24145** |
|---|---:|---:|---:|
| 支出金額 x0 | 240.0 | 240.0 | **301.9** |
| 存入金額 x0 | 286.4 | 286.4 | **358.4** |
| 帳面餘額 x0 | 330.8 | 330.8 | **417.6** |

同一家銀行、同一個系統匯出、同一個查詢期間 —— 整張表右移了 62pt。
（欄寬會跟著內容自動撐開，24145 的交易說明比較長。）

**所以座標不能寫死。每一份 PDF 自己讀表頭，用讀到的位置切欄。**
要驗的是**相對關係**（支出在存入左邊、存入在餘額左邊），不是絕對位置。

### 這幾項為什麼全都是「擋」

上一版我把餘額連續與總計列為「警告，人確認後仍可匯入」。
實測之後改成全擋 —— 因為三份 PDF 全部一次就通過，
**沒過就代表解析器真的錯了**，不是資料本身有瑕疵。

放行的話，錯的流水會進資料庫，而餘額歪掉是「慢慢地、不報錯地」發生。
真的遇到擋不下來又必須匯的情況，那時再開特例，並記在 `warnings` 欄。

## 四、解析：三個會安靜漏資料的坑

### 坑① 純文字看不出支出還是存入

抽出來的文字長這樣：

```
1  2025/01/02 ＡＴＭ轉 台北富邦  17,836  45,943
11 2025/02/10 企網付款          217,575 44,334
```

**看不出 17,836 是存入、217,575 是支出** —— 兩欄之間的空白在純文字裡消失了。

x 座標分得出來（70564）：`17,836` 右緣 x1=325.4 落在存入欄，
`217,575` 右緣 x1=279.0 落在支出欄，餘額一律 x1=367.1。

金額**靠右對齊**，所以用「右緣 x1」比「左緣 x0」穩 ——
位數不同的數字左緣會飄，右緣不會。

**判錯一筆的後果**：那一筆之後的餘額全部偏掉兩倍金額，
而且**不會報錯** —— 只會讓卡片上的數字慢慢跟銀行對不上。

### 坑② 表頭只印在第 1 頁

48088 有 6 頁：

```
p1  表頭=['支出金額','存入金額','帳面餘額']   ← 只有這一頁有
p2  表頭=[]
p3  表頭=[]
p4  表頭=[]   ← 資料照樣印，沒有表頭
p5  表頭=[]
p6  表頭=[]
```

「找不到表頭就跳過這一頁」是最自然的寫法 ——
**而那會讓 198 筆只讀到 32 筆，另外 166 筆靜靜消失。**
金額欄位判斷全部正確，總計卻對不上，然後查半天。

**第 1 頁讀到的欄位位置要記下來，後面每一頁沿用。**

### 坑③ 票據號碼在餘額欄的右邊

```
2025/06/05 7176235030200100     ← 這是票據號碼，x1=547
1 2025/06/05 票據轉帳 1,000,000 1,000,000
13:07:00 0374507                ← 這也是，x1=529
```

只寫「最右邊的數字是餘額」的話，`7176235030200100` 會被當成餘額。

**要有右界**：x1 超過「備註票據號碼」表頭的左緣，就不是金額欄。

### 一筆交易佔三行

```
2025/01/01 012-0000341168247682        ← 交易日 ＋ 票據號碼
1 2025/01/02 ＡＴＭ轉 台北富邦 17,836 45,943   ← 序號 帳務日 說明 行庫 金額 餘額
01:06:44 １２月房租                     ← 時間 ＋ 摘要
```

依 `top` 座標分組，容差 3pt。**中間那行有序號**，靠它認出哪一行是主列。

### 交易日 ≠ 帳務日

`2025/01/01` 交易、`2025/01/02` 入帳 —— **兩個都要存**。
餘額的順序跟著**帳務日**走，對帳時人看的是**交易日**。
只存一個的話，另一種需求出現時就沒有資料了。

### 序號是免費的第三道驗證

PDF 上的序號是 1…N 連續的（三份都驗過）。
**不能拿它當去重鑰匙**（換查詢期間就從 1 重來），
但拿來檢查「有沒有漏讀」剛剛好 —— 坑②那種整頁消失，序號一斷就抓到。

### 期初餘額不用人填

第一筆的「餘額 − 存入 + 支出」就是期初。三份實測：

```
70564   45,943 −    17,836 =  28,107
24145  1,000,000 − 1,000,000 =      0   ← 2025/06 才開戶
48088   84,473 −    79,969 =   4,504
```

人填會填錯，而填錯了整條餘額鏈都對不上，
然後每次匯入都跳警告，最後沒有人再看警告。

## 五、去重

### 鑰匙

```
account_id ＋ 帳務日 ＋ 帳面餘額 ＋ 交易時間
```

**為什麼不用序號**：PDF 上的 `1, 2, 3…` 是**本次查詢的流水號**。
換一個查詢期間就從 1 重來 —— 拿它當鑰匙，第二次上傳會把第一筆蓋掉第一筆。

**為什麼餘額比金額可靠**：同一天可能收兩筆一樣的房租（都是 46,000），金額會撞。
但餘額不會 —— 第一筆之後餘額變了，第二筆的餘額必然不同。

**為什麼還要交易時間**：唯一撞得到的情況是「同一天先進 X 元再出 X 元」，
餘額回到原點。那時靠時間分。

### 重複要看得見，不能靜靜跳過

匯入完要說：

```
這次 47 筆 —— 新增 12 筆、重複 35 筆
                     [看是哪 35 筆]
```

跳過的東西沒有痕跡的話，數字對不上時查不出是「漏了」還是「本來就沒有」。

## 六、資料結構（草案）

```
bank_accounts  帳戶主檔
├ id, name              「元大 70564」
├ bank                  「元大銀行」
├ account_no            20992000170564  ← 上傳時拿 PDF 認到的帳號比對這一欄
├ account_no_tail       末五碼。退路,現在用不到
├ parser                'yuanta'  哪一支解析器（將來換銀行才會有第二支）
├ opening_balance       期初餘額（從第一份對帳單推導,不是人填）
├ sort, active
└ ※ 沒有 balance 欄 —— 餘額讀最新那份對帳單的 closing_balance

bank_statements  上傳批次
├ id, account_id
├ period_from, period_to    PDF 上的查詢期間
├ closing_balance           期末餘額  ← **卡片上的數字讀這裡**
├ total_debit, total_credit footer 的「總計」,驗證用
├ parsed_count              解析出幾筆
├ inserted_count            實際寫入幾筆
├ skipped_count             重複跳過幾筆
├ warnings                  驗不過但人確認後仍匯入的項目
├ file_name
├ uploaded_by, uploaded_at
└ note

bank_transactions  流水
├ id, account_id, statement_id
├ seq                   PDF 上的序號（同日排序 ＋ 檢查有沒有漏讀）
├ txn_date              交易日
├ post_date             帳務日   ← 排序與餘額連續性看這個
├ txn_time              交易時間
├ description           交易說明（ＡＴＭ轉／企網付款／現金存款／存款息…）
├ counterparty          交易行庫（台北富邦／中華郵政…）
├ debit, credit         支出／存入（其中一個是 0）
├ balance               帳面餘額  ← 去重鑰匙的一部分
├ memo                  摘要（１２月房租／南５／林思瑜３月租金…）
├ ref_no                票據號碼
└ created_at

唯一索引：(account_id, post_date, balance, coalesce(txn_time,'00:00:00'))
         ↑ 一定要 coalesce —— null 在唯一索引裡互不相等,
           沒印時間的兩筆會重複匯入
```

### 摘要是將來對帳的線索

```
１２月房租        ← 全形數字
南５             ← 房源代號
林思瑜３月租金     ← 房客名 ＋ 月份
開封店面押租       ← 物業 ＋ 用途
Ｒｅｎｔ ｕｔｉｌｉｔｉｅｓ
```

**全形字要保留原樣存**，不要轉半形 ——
轉了之後跟 PDF 對不起來，而人核對時看的是 PDF。
比對時再轉，那是查詢的事不是儲存的事。

### 解析器跑在瀏覽器（使用者選定 2026-08-18）

```
會計拖 PDF 進上傳區
      │
      ▼
瀏覽器用 pdfjs 解析 ← 不上傳檔案，PDF 沒離開他的電腦
      │
      ▼
當場顯示預覽：認到哪個帳戶、幾筆、期間、新增/重複
      │
      ▼
按確認 → 只送解析結果的 JSON 給後端
      │
      ▼
**後端重驗一次**：餘額鏈 ＋ 總計 ＋ 序號連續 → 才寫入
```

**為什麼是瀏覽器**：pdfjs 本來就是瀏覽器函式庫，在它的原生環境跑最不會出意外。
伺服器不用裝 Python，部署不變。而且預覽是即時的 —— 檔案根本不用上傳一趟。

**代價，講在前面**：解析是在前端算的，後端收到的是一包 JSON。
所以**後端一定要重驗**，不能因為「前端已經驗過」就直接寫入 ——
不然任何人打 API 都能塞流水進去。三道驗證是純算術，在後端跑一次很便宜。

還有一個小代價：pdfjs 的 `getTextContent()` 回傳「文字塊」不是「詞」。
如果它把 `1 2025/01/02 ＡＴＭ轉 台北富邦` 併成一塊，x 座標就抓不到單一數字。
**這是實作第一步要先確認的事**，用 70564 那份試一次就知道 ——
併成一塊的話還有 `textContent.items` 的 `chars` 層可以退，但寫法會不一樣。

### 解析器一定要有的測試

支出／存入判反**不會報錯**，只會讓餘額慢慢跟銀行對不上。
所以測試要釘住的不是「解析得出東西」，而是：

**用三份真實 PDF 當測試資料**，每一份都釘住上表那六個數字。
另外針對三個坑各釘一條：

- `17,836` 在存入欄的 x 位置 → `credit`，`debit` 是 0；`217,575` → `debit`
- **48088 要讀滿 198 筆**（坑②：表頭只在第 1 頁，跳過無表頭的頁只會讀到 32 筆）
- **24145 的表頭 x 座標跟另外兩份差 62pt 也要能解析**（坑①的變體：座標不能寫死）
- `7176235030200100` 不可以被當成餘額（坑③：票據號碼在右邊）
- 24145 的期初推導出 0，不是 null 也不是 1,000,000
