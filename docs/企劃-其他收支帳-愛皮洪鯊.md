# 企劃：其他收支帳（愛皮 · 洪鯊）

> **狀態：企劃中，尚未動工。**（2026-08-22）
> 使用者已確認的四件事寫在〈已拍板〉。〈待確認〉那幾條沒答之前不要開工。

---

## 一、要解決什麼

現在系統裡的收入與支出**全部是安幸的**。愛皮與洪鯊這兩家的錢目前沒有地方記，
或是混著記在安幸帳上。

需求（使用者原話）：

> 目前 收入 與 請款 都是安幸，我需要多一個介面 給 愛皮 洪鯊，
> 流程一樣、同一個介面填寫，但是變成 收入與支出時，
> 把洪鯊與愛皮獨立出來，在一個新的 Menu 叫「其他收支帳」

拆成五件事：

| # | 需求 |
|---|---|
| 3 | 同一套介面填寫，收支時分流到新選單「其他收支帳」 |
| 4 | 一次性收入的「物業」多一個「其他」，之後可選愛皮／洪鯊 |
| 5 | 請款的「用途」多加愛皮／洪鯊 |
| 6 | 愛皮洪鯊的請款只要總經理核可；支出認列進其他收支帳，分兩個 tab，完整 filter |
| 7 | 其他收支帳的權限：會計 ＋ 總經理 |

## 二、已拍板（2026-08-22 使用者確認）

| 問題 | 決定 |
|---|---|
| 愛皮洪鯊在資料庫裡是什麼 | **新增一個「帳本」欄位**，不是新物業、不是新表 |
| 主管那一票怎麼辦 | **直接免掉**。送出後只等總經理 |
| 其他收支帳能不能直接新增 | **可以** —— 兩個入口 |
| 一次性收入選愛皮時房源欄 | **整欄藏起來** |

### 為什麼是「帳本欄位」而不是新物業

當成新物業（`estates` 各建一筆）不用改 schema，但「物業」這個詞會同時代表
**房子**與**公司** —— 之後算坪效、排班、房源評價、清潔記錄都會掃到它們，
而每一支都要記得排除。漏掉一支不會報錯，只會有一份報表悄悄多算兩家公司。

當成完全分開的表（`other_orders` / `other_expenses`）最乾淨，但每一支觸發器、
每一張報表都要寫兩份，維護成本是兩倍。

一個 `book` 欄位是中間解：資料在同一張表，報表靠篩選分開。

## 三、資料模型

### 3.1 新欄位

```sql
-- 三張表各加一欄
alter table public.orders            add column book text not null default 'anxing';
alter table public.expenses          add column book text not null default 'anxing';
alter table public.purchase_requests add column book text not null default 'anxing';

-- 用 CHECK 不用 enum
alter table public.orders add constraint orders_book_chk
  check (book in ('anxing', 'aipi', 'hongsha'));
```

**為什麼是 `text` ＋ CHECK，不是 enum**
之後多一家公司時 enum 要 `ALTER TYPE ... ADD VALUE`，那**不能在交易裡跑** ——
而 SQL Editor 把整份腳本包在一個交易裡。CHECK 改一行就好。

**既有資料全部 `default 'anxing'`** —— 舊資料與現有畫面完全不變。

### 3.2 `book` 怎麼被決定

★ **不讓人多選一個欄位**，由既有的「用途 / 物業」推導。填單的人本來就要選用途。

| 使用者選的 | 存進去 |
|---|---|
| 請款「用途」＝ 愛皮 | `book = 'aipi'` |
| 請款「用途」＝ 洪鯊 | `book = 'hongsha'` |
| 一次性收入「物業」＝ 其他 → 愛皮 | `book = 'aipi'` |
| 其他（正隆、時兆、安幸辦公室…） | `book = 'anxing'` |

推導寫在**觸發器**，不是前端 —— 前端算的話，改前端就能把愛皮的錢記進安幸帳。

> ⚠ **這裡有一條沒決定的**：愛皮／洪鯊在 `estates` 裡要不要真的有一列？
> 見〈待確認〉Q1。

### 3.3 請款單一張只能有一個帳本

一張請款單的項目**不能一半愛皮一半安幸** —— 那樣支出產生時一筆單會拆進兩本帳，
而總額對不起來時沒有人知道該去哪一本查。

做法：第一個項目選了用途之後，其餘項目的用途下拉**只留同一本帳的選項**。
擋在觸發器：`purchase_request_items` 的用途推導出來的 book 必須一致。

## 四、審核規則

| | 安幸 | 愛皮 / 洪鯊 |
|---|---|---|
| 主管票 | 要 | **免** |
| 總經理票 | 要 | 要 |
| NT$ 3,000 免核門檻 | 有 | 有（維持現狀） |

改的是 `pr_apply_status()`（`migration_30` 建的，`threshold numeric := 3000`）。

**寫在觸發器不是前端。** 前端算的話，改前端就能繞過審核 ——
這條規則整個專案都一致（見 README 二、2.3）。

**畫面上要講出來。** 愛皮洪鯊的單在核可進度那一格要顯示

```
✓ 總經理・Jim        （主管免核）
```

不寫「主管免核」的話，看的人會以為那一票還沒投。

## 五、頁面

### 5.1 新選單「其他收支帳」

| | |
|---|---|
| 路徑 | `/otherbooks`（暫定） |
| icon | 需要一顆**不跟 🏦 🤑 💸 💰 撞的** —— 見〈待確認〉Q4 |
| 權限 | 會計 ＋ 總經理 |
| 位置 | 建議放在「帳戶明細」之後、「財務儀錶板」之前 —— 跟錢的那一組在一起 |

```
其他收支帳
├─ 愛皮   ├─ 收入   完整 filter（月份、科目、關鍵字、金額）
│         └─ 支出   完整 filter
└─ 洪鯊   ├─ 收入
          └─ 支出
```

**可以直接新增**（使用者確認）。填單表單**抽成共用元件**給訂單頁／請款頁／這一頁共用 ——
各寫一份的話之後加欄位會漏改一邊，而漏改不會報錯。

### 5.2 一次性收入的「物業」

```
物業 ▾
  ─────────
  正隆
  時兆
  開封
  …
  ─────────
  安幸辦公室
  其他 ▸ 愛皮
       ▸ 洪鯊
```

選了愛皮／洪鯊時**房源欄整欄藏起來**（使用者確認）——
它們沒有房源可言，留一個永遠選不到東西的下拉只會讓人以為壞了。

### 5.3 請款的「用途」

同一份清單加兩項。用途決定 book，所以下拉要分組，讓人看得出來這兩個是不同性質的：

```
用途 ▾
  安幸辦公室
  正隆 / 時兆 / 開封 / …
  ───── 其他帳本 ─────
  愛皮
  洪鯊
```

## 六、影響範圍 —— 這是最容易出錯的一段

**現有的每一支收入／支出查詢，如果不加 `book = 'anxing'`，
愛皮洪鯊的錢會混進安幸的數字裡，而金額看起來完全正常。**

### 要改的檔案

讀 `orders`（收入側）：

| 檔案 | 要不要加篩選 |
|---|---|
| `src/app/(app)/revenues/*` | ✅ 一定要 |
| `src/app/(app)/dashboard/page.tsx` | ✅ 一定要 |
| `src/app/(app)/shortterm/page.tsx` | ✅ 一定要 |
| `src/app/(app)/contracts/page.tsx` | 契約不會有愛皮，但加了比較保險 |
| `src/components/RecurringPanel.tsx` | ✅ |
| `src/components/OrderPayments.tsx` | 子查詢，跟著母單走 |
| `src/components/DepositFees.tsx` | 押金只有安幸，不用改 |
| `src/app/api/import/*` | 匯入一律 `anxing` |

讀 `expenses`（支出側）：

| 檔案 | |
|---|---|
| `src/app/(app)/expenses/page.tsx` | ✅ 一定要 |
| `src/app/(app)/dashboard/page.tsx` | ✅ 一定要 |
| `src/components/DeferralPanel.tsx` | 跟著母單走 |

還有資料庫那側：

- `revenue_recognitions` 由觸發器從 `orders` 產生 —— **要不要也帶 book？** 見〈待確認〉Q2
- `revenue_snapshots` 歷史快照 —— 已經產生的都是安幸，不用回填

### 建議做法：篩選集中在一個地方

不要在十幾個檔案各寫一次 `.eq('book', 'anxing')`。寫一支：

```ts
// src/lib/book.ts
export const BOOKS = ['anxing', 'aipi', 'hongsha'] as const;
export const BOOK_LABEL = { anxing: '安幸', aipi: '愛皮', hongsha: '洪鯊' };
/** 沒指定就是安幸 —— 舊查詢加上這個之後行為不變 */
export const onlyBook = (q, book = 'anxing') => q.eq('book', book);
```

漏改一支的成本是「某張報表多算兩家公司的錢」，而那個錯誤**不會報錯**。

## 七、施工順序

| # | 做什麼 | 為什麼是這個順序 |
|---:|---|---|
| 1 | migration：`book` 欄位 ＋ CHECK ＋ 回填 `anxing` | 欄位先有，後面才有東西可以篩 |
| 2 | migration：用途 → book 的推導觸發器 ＋ 審核規則改寫 | 規則在資料庫，前端才不可能繞過 |
| 3 | `src/lib/book.ts` ＋ 測試 | 純函式先寫，後面三步都靠它 |
| 4 | **把既有報表全部加上 `book` 篩選** | ★ 排在新功能**前面** —— 先確保安幸的數字不會被污染，再開新入口 |
| 5 | 填單表單：用途／物業加選項，房源欄條件隱藏 | |
| 6 | 新頁面「其他收支帳」 | 最後做 —— 前面都對了它才有意義 |
| 7 | 驗證：tsc、測試、報表數字比對 | 改之前先記下營收表與儀錶板的數字，改完要一模一樣 |

**第 4 步排在新功能前面是刻意的。** 反過來做的話，中間那段時間愛皮的錢
已經進資料庫但報表還沒篩，安幸的數字會錯 —— 而且不會有人發現。

## 八、待確認（開工前要答）

| # | 問題 | 為什麼要先答 |
|---|---|---|
| **Q1** | 愛皮／洪鯊要不要在 `estates` 裡真的有一列？ | 有的話 `estate_id` 有值，既有的「按物業分組」報表會冒出兩家公司；沒有的話 `estate_id` 是 null，而現在有些查詢假設它不是 null |

## 九、風險

| 風險 | 嚴重度 | 對策 |
|---|:---:|---|
| 報表漏加 `book` 篩選 → 安幸數字被污染 | 🔴 | 篩選集中在 `lib/book.ts`；第 4 步排在新功能前；改前改後比對數字 |
| 一張請款單混兩本帳 | 🟠 | 觸發器擋，第二個項目起限制用途選項 |
| 前端算 book 而不是觸發器 | 🟠 | 一律寫在資料庫 |
| 「主管免核」沒顯示 → 以為那票還沒投 | 🟡 | 核可進度那格明寫「主管免核」 |
| 新頁面與既有填單表單各寫一份 | 🟡 | 抽共用元件 |

## 十、不在這次範圍

- 跨帳本的轉帳（安幸代墊愛皮的錢之類）—— 真的有這種事要另外規劃
