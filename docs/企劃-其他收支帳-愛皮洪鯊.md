## 一、要解決什麼

現在系統裡的收入與支出**全部是安幸的**。愛皮與洪鯊這兩家的錢沒有地方記。

| | 業務 | 跟安幸的關係 |
|---|---|---|
| **安幸** | 包租代管 | 現有系統 |
| **洪鯊** | 投資公司 | 沒有房子、沒有房客、沒有押金 |
| **愛皮** | 旅行社 | 同上 |

需求：**同一套介面填寫**，但收支時分流到新選單「其他收支帳」。

### 2.1 為什麼「另計」是對的

安幸的營收表**不是把訂單金額加起來**的。一筆長租收 12 萬、租期跨 6 個月，
那 12 萬要拆成每個月 2 萬 —— 系統用 `revenue_recognitions` 這張表做這件事，
營收表讀的是它。

**投資公司的股利、旅行社的團費沒有「跨月」這回事。** 收到就是那天的收入。
硬套認列機制只是多一層轉換，而多一層就多一種對不起來的方式。

> 使用者確認（2026-08-22）:「愛皮洪鯊沒有跨月認列問題，目前都是一次性直接收入。」

所以：

| | 安幸 | 愛皮 / 洪鯊 |
|---|---|---|
| 收入怎麼算 | 讀 `revenue_recognitions`（認列） | **直接加總 `orders`**（發生） |
| 支出怎麼算 | 加總 `expenses`（含遞延母子單） | **直接加總 `expenses`** |
| 認列觸發器 | 照跑 | **跳過**（`book <> 'anxing'` 就 return） |

> ⚠ **兩邊的數字不能互相對照。** 安幸看的是「這個月認列多少」，
> 愛皮看的是「這個月實際收多少」。這是刻意的，但報表上要標清楚，
> 不然有人會拿兩個數字相加然後問為什麼跟銀行對不起來。

## 三、資料模型

### 3.1 新欄位

```sql
alter table public.orders            add column book text not null default 'anxing';
alter table public.expenses          add column book text not null default 'anxing';
alter table public.purchase_requests add column book text not null default 'anxing';

alter table public.orders add constraint orders_book_chk
  check (book in ('anxing', 'aipi', 'hongsha'));
```

**為什麼是 `text` ＋ CHECK 不是 enum**
之後多一家公司時 enum 要 `ALTER TYPE ... ADD VALUE`，**那不能在交易裡跑** ——
而 SQL Editor 把整份腳本包在一個交易裡。CHECK 改一行就好。

**既有資料全部 `default 'anxing'`** —— 舊資料與現有畫面完全不變。

### 3.2 `book` 怎麼被寫進去

**不用推導。第二層下拉選什麼就是什麼。**

| 使用者選的 | 存進去 |
|---|---|
| 收入：來源＝其他事業體 → 事業體＝洪鯊 | `book = 'hongsha'` |
| 支出：用途＝其他事業體 → 事業體＝愛皮 | `book = 'aipi'` |
| 其他所有情況 | `book = 'anxing'`（預設值，不用寫） |

★ 但**驗證要在觸發器**：來源是 `other_biz` 卻 `book = 'anxing'` 一律擋下。
前端算的話，改前端就能把愛皮的錢記進安幸帳。

### 3.3 一張請款單只能有一本帳

用途是**每個項目各自選的**，所以一張單理論上可以一項正隆、一項愛皮 ——
那樣支出產生時會拆進兩本帳，而總額對不起來時沒有人知道該去哪一本查。

做法：第一項選了「其他事業體」之後，其餘項目的用途下拉**只留同一本帳的選項**。
擋在觸發器，不只前端。

### 3.4 會計科目要分家

`account_codes` 加一欄 `book`，各家只看得到自己的科目（見第八段）。

## 五、頁面

### 5.1 新選單「其他收支帳」

| | |
|---|---|
| 路徑 | `/otherbooks` |
| icon | **🗂️** |
| 權限 | 會計 ＋ 總經理 |
| 位置 | 「帳戶明細」之後、「財務儀錶板」之前 |

```
其他收支帳
├─ 愛皮  ├─ 總覽（儀錶板，見第七段）
│        ├─ 收入   完整 filter
│        └─ 支出   完整 filter
└─ 洪鯊  （同上三個）
```

填單表單**抽成共用元件**給訂單頁／請款頁／這一頁共用 ——
各寫一份的話之後加欄位會漏改一邊，而漏改不會報錯。

### 5.2 收入：來源多一項，物業欄換身分

```
來源 ▾                          物業 ▾
  私下                            正隆 / 時兆 / 開封 …
  其他收入
  其他事業體收入  ← 新增
```

選了「其他事業體收入」之後，**右邊那一欄標籤改成「事業體」**：

```
來源 ▾                          事業體 ▾ *
  其他事業體收入                   洪鯊
                                 愛皮
```

**表單形狀照「其他收入」那一種**（單一「日期（認列月份）」），
不是「私下」那種起日／迄日 —— 兩家都是一次性收入，沒有租期可言。

藏起來的欄位:

| 欄位 | 為什麼藏 |
|---|---|
| 房源 | 沒有房子 |
| **押金** | 不收押金。留著會有人誤填，而誤填的押金會跑進押金管理頁變成一筆要退的錢 |
| 起日／迄日 | 一次性收入只要一個日期 |

保留的:房客（＝客戶／標的名稱）、日期、金額、會計科目、項目、收款方式、
需開立發票、備註。

> **為什麼切換點在「來源」而不是在物業清單裡加一群**
> 事業體混在物業清單裡的話，遲早有人把「愛皮」當成一棟房子選下去。
> 來源是這張表單本來就會先選的欄位，在那裡分流最自然。

**新的 `source` 值 `other_biz`。** 它會出現在營收表的來源篩選與顏色標籤裡 ——
一眼看得出哪幾筆不是安幸的。

### 5.3 支出：用途多一層

```
用途 ▾
  安幸辦公室
  正隆 / 時兆 / 開封 / …
  其他事業體  ← 選了之後多出第二層

    事業體 ▾   洪鯊 / 愛皮
```

`purpose_type` 多一個值 `other_biz`，此時 `estate_id` 與 `property_id` 都是 null
（跟 `office` 同一套規則）。

## 六、影響範圍 —— 最容易出錯的一段

**現有的每一支收入／支出查詢，如果不加 `book = 'anxing'`，
愛皮洪鯊的錢會混進安幸的數字裡，而金額看起來完全正常。**

### 實際改了哪些（2026-08-22 完成）

**比預期少很多** —— 有幾支在資料庫層就分乾淨了。

| 檔案 | 動作 | 為什麼 |
|---|---|---|
| `dashboard/page.tsx` | ✅ **改了 5 處** | 支出、訂單、待付款、比較期的支出與訂單 |
| `expenses/page.tsx` | ✅ **改了主查詢** | 三家的支出住同一張表，非擋不可 |
| `components/RecurringPanel.tsx` | ✅ 加了（保險） | `imported_via='recurring'` 目前不可能是別的帳本，但一行的事 |
| `shortterm/page.tsx` | ⭕ **不用改** | 清單走 `.in('source', SRC)`，而 `SRC` 不含 `other_biz` —— **已經自動排除**。在 SRC 上加了警告註解 |
| `revenues/*` | ⭕ **不用改** | 讀 `revenue_recognitions`，而非安幸的訂單根本不會產生認列（migration_161）。**資料庫層就擋掉了** |
| `revenues/row-drawer.tsx` | ⭕ 不用改 | 用 order id 單筆查詢，從認列列下鑽 —— 進不來非安幸的 |
| `contracts/page.tsx` | ⭕ 不用改 | 全部走 `contract_id`，而兩家沒有契約 |
| `components/OrderPayments.tsx` | ⭕ 不用改 | 走 `parent_order_id`，跟著母單 |
| `components/DeferralPanel.tsx` | ⭕ 不用改 | 走 `parent_expense_id`，跟著母單 |
| `api/import/*` | ⭕ 不用改 | 沒寫 `book` 就是 `anxing`（default） |

> **營收表不用改是這次設計最好的一點。** 規則寫在資料庫（認列觸發器只跑安幸），
> 前端一行都不用動 —— 而且之後不管誰寫新的營收查詢，都不可能撈到愛皮的錢。
>
> 反過來說:**支出那側沒有這種保護**，因為 `expenses` 是三家共用的一張表，
> 沒有中間層。所以支出的每一支查詢都要自己記得帶 book。

### 篩選集中在一個地方

不要在十幾個檔案各寫一次 `.eq('book', 'anxing')`：

```ts
// src/lib/book.ts
export const BOOKS = ['anxing', 'aipi', 'hongsha'] as const;
export type Book = (typeof BOOKS)[number];
export const BOOK_LABEL: Record<Book, string> =
  { anxing: '安幸', aipi: '愛皮', hongsha: '洪鯊' };
/** 沒指定就是安幸 —— 既有查詢加上它之後行為不變 */
export const onlyBook = <T>(q: T, book: Book = 'anxing') => (q as any).eq('book', book) as T;
```

漏改一支的成本是「某張報表多算兩家公司的錢」，而那個錯誤**不會報錯**。

## 七、其他收支帳的儀錶板

安幸的財務儀錶板有遞延、認列、母子單那一整套。**這裡不要照抄** ——
兩家公司的帳單純很多，抄過來只會是一堆永遠是 0 的欄位。

### 7.1 版面

```
┌─ 愛皮 · 2026 年 8 月 ─────────────────────────┐
│                                               │
│   收入          支出          淨額            │
│   $284,000     $196,500      $87,500          │
│   ▲ 12%        ▼ 3%          ▲ 41%   （vs 上月）│
│                                               │
├───────────────────────────────────────────────┤
│  近 12 個月                                   │
│  ▁▂▃▅▄▆█▅▃▄▆█   收入                          │
│  ▁▁▂▃▂▄▅▃▂▃▄▅   支出                          │
├───────────────────────────────────────────────┤
│  本月收入 by 科目        本月支出 by 科目      │
│  團費收入    198,000     機票款      142,000  │
│  票券佣金     54,000     住宿款       38,000  │
│  簽證代辦     32,000     平台手續費   16,500  │
├───────────────────────────────────────────────┤
│  還沒收的錢              還沒付的錢            │
│  3 筆 · $46,000          2 筆 · $28,000       │
└───────────────────────────────────────────────┘
```

### 7.2 四塊各自回答一個問題

| 區塊 | 回答什麼 | 資料來源 |
|---|---|---|
| 三個數字 | 這個月賺不賺錢 | `orders` / `expenses` 直接加總（**不是認列** —— 兩家都是一次性收入） |
| 近 12 個月 | 趨勢是往上還往下 | 同上，按 `checkin` / `spent_on` 分月 |
| by 科目 | 錢花在哪、賺在哪 | `account_code` 分組，只列前 5 名 |
| 還沒收／還沒付 | 現在該追誰 | `orders.paid = false` / `purchase_requests` 未出款 |

**「還沒收的錢」是這張表上最有行動力的一格** —— 其餘三塊是回顧，
只有它會讓人今天做一件事。所以它不藏在底下的分頁裡。

### 7.3 刻意不做的

| 不做 | 為什麼 |
|---|---|
| 遞延認列 | 兩家沒有跨月的錢（見 2.1） |
| 母子單 | 沒有加費、沒有移房 |
| 房源 / 物業維度 | 沒有房子 |
| 跟安幸並排比較 | 算法不同（認列 vs 發生），並排會誤導 |

## 十、風險

| 風險 | 嚴重度 | 對策 |
|---|:---:|---|
| 報表漏加 `book` 篩選 → 安幸數字被污染 | 🔴 | 集中在 `lib/book.ts`；第 5 步排在新功能前；改前改後比對數字 |
| 認列觸發器沒跳過非安幸 → 愛皮的錢被拆成月認列 | 🔴 | 觸發器第一行就 return；自檢查 `revenue_recognitions` 裡有沒有非安幸的列 |
| 一張請款單混兩本帳 | 🟠 | 觸發器擋，第二項起限制選項 |
| 前端寫 book 而沒有觸發器驗證 | 🟠 | 來源／用途與 book 不一致一律擋下 |
| 科目草案沒給記帳士看就上線 | 🟠 | 第八段標明是草案 |
| 「主管免核」沒顯示 | 🟡 | 核可進度那格明寫 |
| 填單表單各寫一份 | 🟡 | 抽共用元件 |

## 十一、不在範圍（2026-08-22 使用者確認）

**這五條不是「假設」，是使用者明確排除的。**

| 排除的 | 使用者原話 | 因此可以怎麼做 |
|---|---|---|
| 押金 | 「沒押金」 | 收入表單的押金欄**整區藏掉**，不用做「選了事業體才隱藏」的條件判斷 —— 那條路本來就不存在 |
| 契約與房源 | 「沒有房源」 | `estate_id` / `property_id` 一律 null。契約頁完全不用動 |
| 跨帳本轉帳 | 「不用」 | 不需要 `transfer_book` 之類的欄位，也不用處理「安幸代墊」的沖銷 |
| 三家合併報表 | 「不用」 | 儀錶板一次只看一家，不做並排比較（本來就會誤導，見 7.3） |
| 稅務申報功能 | 「不用」 | 科目只要「系統分得開」就夠，不用對到申報書的格式 |

### 這五條省掉了什麼

不是隨口確認 —— 每一條都直接砍掉一段工：

- **沒押金** → 不用碰 `deposits` 的任何觸發器與 RLS
- **沒房源** → 不用處理「按物業分組」的報表怎麼顯示一家公司
- **不跨帳本** → 不用設計沖銷邏輯（那才是真正難的部分:一筆錢同時是安幸的支出與愛皮的收入，兩本帳都要對得起來）
- **不合併** → 不用解決「認列 vs 發生兩種算法怎麼加在一起」這個沒有正確答案的問題
- **不報稅** → 科目可以照實務命名，不用遷就申報書

> ⚠ **哪天要做跨帳本轉帳，這份企劃要重寫一大段。** 那不是加一個欄位的事 ——
> 一筆代墊在安幸是支出、在愛皮是收入，中間還有還款。三本帳要同時對得起來，
> 而任何一邊漏記都不會報錯。真的要做的話請當成一個新專案。
